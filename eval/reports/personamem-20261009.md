## PersonaMem-v2 检索记忆输入修复（2026-10-06）

### 问题与最终行为

原始数据集的 MCQ 路径在 `_build_personamem_items` 中注入完整原始对话，
Search 结果只写入未被归档答案函数读取的字段。因而此前成绩无法衡量 Add/Search 改进。

修复后：原始对话用于 Add；每题 Search 结果按返回顺序、已有 token 前缀预算渲染为
`retrieved_context`，适配器将其转换为归档函数读取的 `chat_history`。
模型仍收到官方问题与选项模板，选项构造、洗牌、正确选项映射和 `evaluate_mcq` 保持不变。
尾部 system 消息继续使用既有网关兼容折叠。

- 空检索只显示 `(no memories)`，不会回填原始对话或另一字段的旧记忆。
- 缺少检索字段或字段类型错误直接失败，不能静默使用完整历史。
- 答案记录标识 `personamem-search-memory-v1` 并保存逐题输入指纹。
  旧答案或变更后的输入不能按 id 静默跳过，要求新 run-id。
- 官方采集重放的 PersonaMem 开放题入口已有检索注入；该入口和其裁判未修改。
- 归档 `benchmark_data/pipeline_v2_personamem.py` 保持原样；修改的是仓库内适配器。

这是本地检索评测的答案输入口径变更，不证明 AML 线上采用相同注入方式。
此前完整历史精度不能直接与新口径比较；原七数据集结果也没有加入 PersonaMem。

### 验证

真实答案与官方 MCQ 判分冒烟：**Qwen/Qwen3.5-9B，2/2 正确**。
两题将原始历史与检索记忆设成相反的晨间活动偏好（瑜伽 / 游泳），
模型均按检索记忆选择；发出前也检查了隐藏原始历史没有进入消息。
这是合成案例的输入链路验证，不是数据集精度，也未运行完整 Add/Search 基准。

`retrieval.memory_controls` 开关不同，不改摘要、状态引句或多跳策略。

回答为 Qwen3.5-9B，两臂同一 persona 使用同一服务器。先前 555 条答案内容

| --- | ---: | ---: | ---: |

### 干扰一：跨进程选项洗牌没有冻结

官方 `official_mcq_options()` 用 `hash(persona_id + question)` 给随机洗牌设种子。
此前只核查了同一进程内的重复调用，漏查 Python hash 在不同进程间的差异。
两臂回答是独立子进程：**938 道改变检索输入的题里，902 道还改变了选项顺序**。
正确选项文本集合完全相同，官方用各自保存的映射判分；没有金标串位问题，
但排序位置会影响模型选择和推理长度，因而不满足纯开关消融。

对同一题另做不调用模型的快速验证：不固定 `PYTHONHASHSEED` 时，三个子进程
产生三个不同映射；固定为 `0` 后，三个进程映射完全相同。
见 洗牌探针（历史路径：`runs/personamem-forgetting-20261009/option-shuffle-probe.json`）。

改变输入且恰好保持相同选项顺序的题只有 36 道，赢 1、输 4、平 31。
这是事后小子集，不能替代完整冻结对照，也不能从中推断平台收益。
原始 1,048 题成绩保留，不筛掉顺序变化题重新包装一个总分。

### 干扰二：大量回答没有输出最终选项

官方 `extract_final_letter()` 没有解析出选项的题，基线 536、开启后 504，分别
占 51.15% 和 48.09%。它们在原始全量分母中按未答对计入，没有被漏掉。
本地适配器输出预算固定为 512 token；模型经常先输出长分析，部分原始答案
明显停在分析中或 `Final` 半句。旧记录没有保存 `finish_reason` 或 `usage`，
**不能把所有未解析答案都确诊为 token 截断**，更不能称作网络失败。

85 道赢题中，71 道是基线未解析而新答案可解析且正确；122 道输题中，85 道
是基线正确而新答案未解析。两边都能解析最终选项的翻转为赢 14、输 37。
这些是事后归因描述，不是改判分或以“可解析题”为分母重算总分。

具体例子：

- `pm-318-6`（屋顶休息区设计）：基线最终输出正确 C；新答案分析已经说 C
  遵守“不依赖现代主义偏好”的要求，却结束于 `Final`，官方无法读到选项。
  这道“输题”不能直接解释成遗忘理解变差。
- `pm-494-2`（旅行期间组织任务）：基线分析已经判断 B 正确，但没有最终
  选项；新答案补出 `Final Answer: B`，形成一题“赢”。这也不足以证明抑制改善。

### 规则的真实问题：识别范围窄，控制句与偏好没有分开

现有实现是确定性规则：主要识别 `forget my…`，按完整 target 或明确属性值
做字面抑制，**没有调用 LLM 做语义归并**。此前全历史表面审计发现：3,583 条
以 Please forget/Forget 开头的用户消息中，688 条符合该整句正则；这只是
表面语法命中，不是 688 条目标都被正确忘掉。

真实样例说明两个缺口：

1. **未识别自然句式。** `pm-737-3` 明确出现
   `Please forget that I appreciate handmade crafts and artisanal goods.`。
   开启后，该句和旧的手作陶瓷杯 / 匠人蜡烛建议都仍在 Search 证据中。
   基线选了不锈钢厨具，新答案选了本地匠人的手工陶瓷碗，并在理由中使用
   artisanal craftsmanship。此题同时改变了选项顺序，不能把翻转完全归因于
   开关；但**相关旧偏好并未被抑制**是可以直接从返回片段确认的。
2. **删了命令，没有删掉同义旧偏好。** `pm-39-4` 的用户命令是
   `Please forget my preference about loving bold abstract graphic novels.`。
   开启后用户命令行被移除，但旧助手建议
   `If you love bold, abstract graphic novels…` 仍在，助手的遗忘确认也仍在。
   完整 target `preference about loving…` 与旧偏好的表达并不相同。
   因而“命令被移除”不能当作“被要求忘掉的信息被抑制”。

检索记录 ID 顺序和返回数量在 1,048 题上全部保持相同；两臂总输入字符数仅
减少约 0.27%。该计数只描述编辑量，不是成功遗忘率。样例中的风险是：
旧偏好证据仍可见，直接用户控制指令却被删掉，下游只能继续自行判断约束。

此前三组真实片段 HTTP 快速检查也均为两臂逐字相同，未证明规则作用于这些
自然遗忘表达。合成探针 **4/18 → 18/18** 是真实的本地边界行为改善，覆盖
简单属性、旧记录重放、重新授权和用户隔离；它不能推广成真实偏好遗忘题提分。
