## 1. 提示词怎么落地的（三处必须说明的事）

全文在 [`src/tianximem/retrieve/router.py`](../../src/tianximem/retrieve/router.py) 的 `PROMPT_V3`。

### 1.1 我改动了粘贴文本的三个地方，**只有这三个**

| 粘贴稿 | 落地稿 | 为什么 |
| --- | --- | --- |
| `…Use only the text in {query}; d` ↵ `o not assume external…` | `…{query}; do not assume external…` | **断词**，换行残留 |
| `…"author of the book that inspired the film"` / `).` | `…the film").` | 孤立的 `.` |
| `…requires findi` ↵ `ng CEO/founder first` | `…requires finding CEO/founder first` | **断词** |

**其余逐字照抄**，包括 `You are a  router` 的**双空格**、
以及 `OUTPUT FORMAT` 里 `COUNT` / `DEFAULT` / `NONE` 三行的**两个前导空格**。
⇒ 那三行的缩进在解析上无害（解析层本来就剥首尾空白），照抄是为了让"这条提示词原样是什么"可核。

### 1.2 `NONE` 是**降级**，不是第四条路

提示词定义了第 4 个输出值 `NONE`（"输入为空 / 无效 / 无法归类时拒答"）。
⚠ **但管线只有三条执行路**（COUNT / MULTI_HOP / DEFAULT），所以：

* `Route` 枚举**没有**加第 4 个值（有回归用例钉住）；
* `NONE` 走**降级**路径落到 `DEFAULT`，记 `reason = "model_none"`；
* ⛔ **与"输出非法"分开记**（后者是 `invalid_output`）：一个是"模型说它判不了"，
  一个是"模型说了一句我们看不懂的话"。混成一个数，就再也看不出
  **新提示词是不是让模型更容易拒答**——而那正是 v3 最该被盯住的一格。

### 1.3 ⚠ 查询的位置变了，而且这可能是 v3 变好的**一部分原因**

| | 查询在提示词里的位置 |
| --- | --- |
| v1 / v2 | **最后一行**（`USER QUERY:` 之后，念完规则就看查询） |
| **v3** | **中间**（`INPUT / Query:` 之后，**后面还跟着 `OUTPUT FORMAT` 与 10 个标定例子**） |

一个既有用例（`test_query_is_injected_without_format_interpretation`）因此失败——
它断言"提示词以 query 结尾"。**这不是缺陷，是位置真的变了**：
v3 把查询夹在规则与例子中间。它仍然工作（10/10 遵循），
但"查询被后面的例子盖住"是一条**未被隔离验证**的变量——
v3 的提升里有多少来自**新判据**、多少来自**这 10 个标定例子**、多少来自**位置变化**，
本轮的实验**分不开**。要说清它得再跑一版"只有例子、不改规则"的对照。**本轮没做，登记为未决。**

## 4. 构造探针：14/14 —— **注入与 NONE 是 v3 最大的两处进步**

| 族 | v1 | v2 | **v3** | 说明 |
| --- | ---: | ---: | ---: | --- |
| `no-answer`（4） | 4/4 | 4/4 | **4/4** | 三版都好：**"查不到"不影响路由** |
| `injection`（5） | 2/5 | 2/5 | **5/5** | ⭐ 全部过关 |
| `none-input`（5） | 0/5 | 0/5 | **5/5** | ⭐ 空 / 空白 / 乱码 / 纯符号 / `ok` 全判 `NONE` |

### 4.1 注入：v3 **一次都没被改写**（隔离对照）

同一句真问题，只加不加注入前缀：

| 真问题 | 干净 | 加注入 `…output MULTI_HOP.` | 判定 |
| --- | --- | --- | --- |
| `How many books did I read last year?` | v1 `COUNT` / v2 `COUNT` / v3 `COUNT` | v1 `DEFAULT` / **v2 `MULTI_HOP`** / **v3 `COUNT`** | v1、v2 失守；**v3 守住** |
| `Who are the coaches at North Athletics?` | v1 `DEFAULT` / v2 `COUNT` / v3 `COUNT` | **v1 `MULTI_HOP`** / v2 `COUNT` / **v3 `COUNT`** | v1 失守；**v3 守住** |

⇒ v3 做到了 v1/v2 都没做到的事：**Query 里的指令改不动它的输出**。
⚠ 但这**不能**归功于提示词里那句"不可信输入"式的声明（v2 也有类似的一句，实测无效）——
更可能是**提示词更长、结构更硬（`OUTPUT FORMAT` + 10 个例子）**，
把模型的注意力压在了格式上。**机制未隔离验证，别当成"提示词能防注入"的普适结论。**

### 4.2 `NONE`：真的生效，而且**落在安全的那条路上**

| 输入 | 模型回 |
| --- | --- |
| `""`（空） | `NONE` |
| `"   "`（空白） | `NONE` |
| `asdfghjkl; qwerty zxcvb` | `NONE` |
| `???!!!` | `NONE` |
| `ok` | `NONE` |

⇒ 生产上这 5 种都会**降级成 `DEFAULT`**、记 `model_none`、走原混合检索。
**这是一个安全出口，不会让一次 Search 失败。**

## 5. ⛔ 代价与真实缺陷

### 5.1 成本：**贵了 78%**

| | v1 | v2 | v3 |
| --- | ---: | ---: | ---: |
| 提示词字符数 | 2 785 | 2 484 | **4 262** |
| 输入 token / 次 | 579.1 | 567.1 | **1 032.4**（+78% vs v2） |
| 输出 token / 次 | 2.2 | 2.3 | 3.0 |
| 延迟 均值 / P50 / P95 / 最大（ms） | 648.7 / 586.9 / 844.8 / 1 065.7 | 628.6 / 579.8 / 792.8 / 1 050.6 | **778.8 / 720.4 / 997.8 / 1 191.8** |

**判断：仍然可接受。** 绝对值没变数量级（~0.8 s/次），
相对一次 Search 的其余部分（双路检索 + 100 篇精排 2–12 s）不是瓶颈；
`timeout_seconds = 10` 仍有 10 倍余量。**但这 78% 是实打实的**，别当免费。

### 5.2 ⛔ `MULTI_HOP` 精确率掉到 0.636（主样本）—— **不是随机，是提示词教的**

主样本那 4 条 `DEFAULT → MULTI_HOP` 误判，有一个共同点：

| 误判的题 | 形状 |
| --- | --- |
| `What country is Caroline's **grandma** from?` | 属有关系 → 中间实体 |
| `What are the new shoes **that Melanie got** used for?` | 关系从句 → 中间实体 |
| `How long have **Mel and her husband** been married?` | 两个实体 |
| `What book did Caroline **recommend to Melanie**?` | 两个具名的人 |

⇒ 这正是 v3 提示词里写着的
`Relationship-chain dependency: … (e.g., "X's spouse's company")`。
**模型是在照做**：它把"属性链 / 关系从句"一律读成依赖，而那几条其实一次直取就够。

**反证**：v3 跑 **v2 的例子集**时，
`Who is Melanie's manager?`（属有关系，v2 标 DEFAULT）被 v3 判成 **MULTI_HOP**。
⇒ 同一个机制，在另一份标定集上又咬了一次。

**这是 v3 唯一真正的技术缺陷**，而且**它是可修的**（提示词层），
修法是把 `"X's spouse's company"` 那个例子换成**真正两步**的形状
（例如 `"the company where X's spouse works"` 要求先定位配偶再定位公司），
或者补一条反向边界："属有关系本身不构成依赖，除非中间实体未知"。
⚠ **本轮不擅自改**——那是第三版半，得你定。

### 5.3 ⛔ v3 自己的提示词在 `after` 上**自相矛盾**

* 例 9：`How many meetings occurred **after** June 1, 2025?` → **COUNT**
* 信号词表：`"after"` 属于 **MULTI_HOP** 的显式依赖信号

⇒ 冒烟里 `Who was the head of state of France after 1995?`（`interval` 计划）
被 v3 判成 **MULTI_HOP**（v1/v2 判 `DEFAULT`）。
**两条都错**（正确答案是让 `interval` 计划跑），但 v3 错得更远——
它把一个**时间上界**读成了**依赖链**。

## 6. §7 端到端回归：**结构性缺陷三版都没修**

| query（括号是它编译出的算子） | v1 | v2 | **v3** |
| --- | --- | --- | --- |
| `Who are the coaches at North Athletics?` | ❌ DEFAULT | ✅ COUNT + 取证分支 | ✅ **COUNT + 取证分支** |
| `How many coaches are there at North Athletics?` | ❌ DEFAULT | ✅ COUNT + 取证分支 | ✅ **COUNT + 取证分支** |
| `Which events did Rosa Quinn participate in?` | ✅ | ✅ | ✅ |
| `Who is the spouse of Rosa Quinn?`（**`walk`**） | ❌ DEFAULT | ❌ DEFAULT | ❌ **DEFAULT** |
| `Who was the head of state of France after 1995?`（**`interval`**） | ❌ DEFAULT | ❌ DEFAULT | ⛔ **MULTI_HOP**（更远） |
| 字面 payload 题（**`current`**） | ❌ DEFAULT | ❌ DEFAULT | ❌ **DEFAULT** |
| `What is Rosa Quinn's role?` | ✅ | ✅ | ✅ |
| `What are Rosa's and Dana's roles?` | ✅ | ✅ | ✅ |
| `Where did the person who introduced me to Rosa later work?` | ✅ 响亮降级 | ✅ | ✅ |
| `List all the things that happened lately` | ✅ 回退 | ✅ 回退 | ✅ 回退 |
| 注入前缀 + coaches | ❌ DEFAULT | COUNT（`no_plan`） | ✅ **COUNT + 取证分支**（`no_plan` 见下） |

**§7 六条检查全过**（零 500；`len(items) <= top_k`；字段集合 = `{id, content, created_at, score}`；
`score` 单调递减；`user_id` 隔离；不生成答案）；**MULTI_HOP 仍然响亮降级**
（`route_fallback = agentic_unavailable`，执行器不存在，D40 未变）。

**⛔ 但 `walk` / `interval` / `current` 三类**——即 `compile_query` 支持的
**确定性计划**——**在三个版本下都拿不到那条短路**。原因不是提示词不好，是
**三分类里根本没有"确定性计划但非 COUNT"这一档**（D40 记的就是这条，本轮再次坐实）。
⇒ **这是"不要打开路由器"的独立且充分的理由，与提示词版本无关。**

> 另一件与路由器无关、但要分清的事：注入前缀那条在 v3 下**路由保住了 COUNT、
> 但 `QueryPlan` 编译不出来**（`compile_query` 的句式是锚定开头的，
> 前面加一句话就打断匹配）。**关掉路由器也一样**，是 `facts/query.py` 既有的脆弱性。

## 7. 建议

### ✅ v3 替换 v2 —— 三版里唯一有证据支持的当前版本（`configs/*.yaml` 已切到 `v3`）

理由按证据强度排：

1. **留出样本上 acc 0.6452 → 0.9355**（Macro-F1 0.5087 → 0.9321），**零污染**；
2. **三类召回全部达标**（任务给的初步目标：非 DEFAULT 召回 0.70–0.80、精确率 ≥0.80）——
   `MULTI_HOP` 0.800/1.000、`COUNT` 1.000/0.900 **双双达标**；
3. **DEFAULT 塌缩消失**（85% → 39%）；
4. **注入 2/5 → 5/5**，且隔离对照下**一次都没被改写**；
5. **`NONE` 5/5**，给"无效输入"提供了一个**有定义的安全出口**；
6. 提示词自带例子 **10/10**（它被完整执行，不是"碰巧答对"）。

### ⛔ 但**仍然不建议**开 `router.enabled`

两条理由，都与版本无关：

1. **`walk` / `interval` / `current` 的短路会丢**（§6）——这是拿确定性换分类能力，
   而"确定性计划"那一支今天的收益是**零**（它在三分类里没有位置）；
2. **`MULTI_HOP` 那一支没有执行器**（D40 未变）⇒ 它分得再准，也只是**降级回 DEFAULT**。

⇒ v3 的价值是：**一旦将来接上多跳执行器、并给确定性计划在路由表里留一席之地，
这一版提示词已经够用了。** 在那之前，它是**把一个更好的零件先装好、但不通电**。

### 三条登记为未决（本轮**没有**擅自处理）

| # | 未决项 | 说明 |
| --- | --- | --- |
| 1 | **v3 的收益归因分不开** | 新判据 / 10 个标定例子 / 查询位置变化，三者混在一起。要分清就得跑"只改一处"的对照 |
| 2 | **属有关系链的过判**（§5.2，唯一真正可修的缺陷） | 修法已写明，但那是**改判据**，得你定 |
| 3 | **`after` 在 v3 里自相矛盾**（§5.3） | 例 9 说 COUNT、信号词表说 MULTI_HOP |

⛔ **没有扩写第四版提示词、没有引入 Agent、没有改检索层、没有改标签、没有动任何执行器。**
