# AML Smoke 跨版本对比

本主题卷记录真实 AML Smoke 的分数、输入可比性与实现差异。平台分数来自用户提供的
结果截图；请求与状态来自本机采集。各项贡献未经消融验证，不将解释性假设写成因果结论。
本次分析没有发起新的 Smoke、Full、Add/Search 重放或模型调用。

## 2026-10-12 与 2026-09-29 最后一轮 Smoke

### 结论

总分 **44.89 → 70.71，增加 25.82 分，相对增加 57.52%**。七项原有能力中六项上升、
E 持平；截图额外列出的 I 流式记忆下降 2.08 分。提升最明显的是 B 和 A。

两轮查询及原始语料高度对齐，支持“在这套 Smoke 输入上系统表现提升”的判断。
最有直接证据的实现变化是记忆分块细化；不能将提升全部归于精排，也不能归于共同事实取证。
这不等同于 Full 的预期分数，更不等同于对全部数据集的稳定改进。

### 两轮定位与输入核对

用户确认旧成绩来自 **9 月 29 日最后一轮 Smoke**。

- 旧采集：`official-add-bodies-2026-09-29-p1.jsonl` 中对应用户的请求，
  北京时间 **21:40:47.674–21:43:41.445**。
- 新采集：清库并重建容器后的 `/data/capture/requests.jsonl`，对应 POST 请求为北京时间
  **20:45:09.862–20:50:01.400**。
- 新镜像：`tianximem:v1.1.1`，镜像标签记录源码 revision **`16cc3b8`**，profile `default`。
- 旧源码参考：当天最后一轮前已提交的 **`a7ed941`**，北京时间 21:23:26。
  **这只是最接近的已知 Git 版本，旧容器镜像摘要及完整运行配置没有随该轮归档，
  不能把源码配置视作旧运行时配置的完整证明。**

| 输入核对 | 结果 |
| --- | --- |
| Search 请求 | 两轮均 48 次、41 个不同 query；query 出现次数完全一致 |
| 用户 | 两轮均 21 个；新旧 user_id 不同，通过每用户 query 多重集和原始 Add 序列对应 |
| Add 请求与消息 | 两轮均 134 次 Add、1,495 条消息；各对应用户的 Add 次数一致 |
| 原始语料 Add | 128 次的 messages 完全相同，包括 role、content、timestamp |
| 平台反馈 Add | 6 次中 4 次完全相同；2 次 DB/ALF 训练轨迹不同 |
| top_k | 两轮全部 48 次 Search 均为 100 |
| 每用户问句顺序 | 18 个用户相同，3 个用户的同组问句顺序不同；这些变化之间没有新 Add，历史输入阶段相同 |
| 服务端 POST 状态 | 两轮全部 134 次 Add、48 次 Search 均为 HTTP 200 |

本轮另有 HEAD `/add` 和 HEAD `/search` 各一次，均为 405；它们不是 POST 业务失败。

因此，不能将本次提升解释成“旧轮 Add 全挂、这轮修好了”。当天更早的 request_id
失败及后来的大批 Full 网关失败不属于这次选定的旧 Smoke，不能混入归因。
输入核对也不能证明平台 Answer/Judge 模型、评分器版本及随机性完全相同。

### 最有证据的变化：记忆块粒度

从旧 commit 获取 `pairing.py`，与当前纯组合函数分别作用于已捕获消息，仅计算块数，
不生成 embedding、不访问 Qdrant、不作答。两轮输入各自得到相同的块数结果；
当前规则的输出总数还与新轮 SQLite 实际行数一致。

| 口径 | 旧组合规则 | 当前组合规则 |
| --- | ---: | ---: |
| 全部 Add 产出块数 | 298 | 1,326 |
| 79 次全 user Add 产出块数 | 79 | 1,097 |
| 其余 Add 产出块数 | 219 | 229 |

总块数变为旧规则的 **4.45 倍**。旧规则先合并连续同 role 消息；全 user 的一次 Add 会塌成一个
大块。D29/D32 后，配不成 QA 的消息各自独立，配对只取 user 段的末条，因而同一事实
更容易成为独立的检索和精排候选，粗块中多个主题的干扰也更少。

这是 A/B/C 同时改善的首要解释性假设，**不是已测出的分块独立贡献**。
还存在排序、扩窗、平台作答与模型服务等共同变化，未做同一配置下的分块消融。

### 哪些解释能成立，哪些不能

**共同事实取证不是本轮直接提分来源。** 新 SQLite 有 1,326 条 `qa_pairs`、
134 条 `applied_batches`、1,326 条覆盖记录，但 **`memory_facts = 0`**。
覆盖记录只表示抽取器扫描过原文，不表示抽到了事实（PRD §6.1 / 当前架构的派生表边界）。
对部署中的 `compile_query` 做无模型纯函数核查：33 次无计划、14 次 walk、1 次 interval，
没有 current 计划。结合空事实表及 `evaluate_evidence` 的空选择回退行为，本轮走的是
原混合检索链，而不是成功的关系事实短路。B 达到满分也不能反过来证明事实图起了作用。

**精排可能参与，但不能说新增打开精排就带来全部提升。** 当前配置确实启用
`Qwen/Qwen3-Reranker-4B`，端点与密钥齐全；9 月 29 日参考 commit 的默认配置同样
`rerank.enabled=true`。旧轮当天曾发生精排 OOM 与降级，但没有该次 Smoke 独立的
精排成功/降级统计，不能认定旧轮完全没精排。
本轮也未设置 `TIANXIMEM_METRICS_PATH`，实际成功/降级次数未落盘；HTTP 200 不证明
精排一定成功，因为失败会回退 RRF。

**关闭扩窗是另一个候选因素。** 源码参考配置的 `neighbor.radius=2`，当前运行配置为 0。
它可减少额外上下文；但全 user 消息没有完整 QA 邻接链，这部分本来就没有扩窗收益。
没有单独消融，不能把全部增分算到关闭扩窗上。

**时间注解并非本次新加。** 两份配置的 `inject_abs_time` 与 `annotate_relatives` 均为 true，
历史到当前的 `common/annotate.py` 没有实质变更。因此 C 的提升不能简单归于“现在
才加绝对日期/相对时间注解”，更可能与时间证据的分块、选择和排列共同有关，仍待验证。

**查询与总预算未扩大。** 参考旧配置及新运行配置均为 prefetch 每路 200、RRF `k=61`、
权重 `[0.5,0.5]`、最大 117,760 token。排序后的确定性截断存在实现修正，可能减少
候选边界波动，尚不能量化其分数贡献。

**本地答案 prompt 改进不能用于解释真实 Smoke。** 本系统只提供 Add/Search，平台完成
Answer/Eval（PRD §2.1）；仓库中本地 harness 的答案提示词变化没有被传给平台。

### I 流式记忆的下降

I 下降 **2.08 分**，是唯一倒退项。采集中的四条在线 QA 反馈，分别为
`locomo1`、`locomo5`、`scriptMem-angry`、`scriptMem-enemy`，两轮对应反馈分数均是
`1,1,1,0`，反馈内容也相同。因此不能将 I 的变化直接解释成这些题的判分变差。

两条训练轨迹均发生内容变化：DB 和 ALF 的回写奖励/训练任务 score 在两轮均为 1，
但 ALF 轨迹由 8 步变为 10 步，动作和工具调用记录不同。说明流式阶段并非逐字相同的
上下文；后续迁移评分及其分母没有从现有采集恢复，不能将这点分差精确归于某个动作。
只有单轮汇总，尚不能判定持续退化趋势。

### 运行代价

下表是服务采集的延迟，不是平台完整任务时长；旧轮已是当天重复 Smoke，缓存冷热、
服务端模型状态不同，不能将其当成严格的性能消融。

| 接口 | 旧轮 p50 | 新轮 p50 | 旧轮最大 | 新轮最大 |
| --- | ---: | ---: | ---: | ---: |
| Add | 58.45ms | 621.4ms | 325.9ms | 12,576.0ms |
| Search | 567.5ms | 988.4ms | 14,368.5ms | 20,993.6ms |

分块变细意味着更多可索引单元，可能增加 embedding 和存储工作；本轮 Add 延迟明显增加。
没有缓存命中计数，不将全部差异归于块数。新轮最长 Search 约 21 秒，采集没有 POST
失败，本次没有 Cloudflare 请求超时的证据；不能据此保证 Full 的长尾也安全。

### 下一步优先级

1. 优先检查 D/G/H 的错误实例：新分分别 56.11 / 55.00 / 58.33，仍是主要短板。
   需要平台逐题反馈或真实 Search 返回证据，区分漏检、旧新事实冲突、排序干扰与平台作答问题。
2. 记录 I 的后续任务结果及阶段，用训练轨迹、迁移测试和 QA 反馈分别定位。
3. 下一次服务启动前配置已有的 metrics 出口，并保留版本、配置及检索输出，才能判断
   精排成功率和实际路径。本次只指出观测缺口，没有修改在线服务或重启。
4. 消融优先使用本地隔离库与冻结输入；不要为分块/精排归因直接消耗新的官方 Smoke/Full。
   官方反馈不用于训练，不加入按题硬编码逻辑（PRD §12.5 / §17.3 P2）。

## 2026-10-12 同日第二轮：Add/Search 请求内容对比

本节比较当天第一轮 **20:45:09.862–20:50:01.400** 与第二轮
**21:49:53.842–21:54:08.441**（北京时间），不是前文的 9 月 29 日跨版本对比。
按每用户 query 多重集与原始 Add 消息指纹建立一一对应，覆盖全部 21 个用户。
核对只读取采集，不发起新的 Smoke、Add/Search 重放或模型调用。

**结论：原始语料、问句和请求参数没有变化，实质文字差异只有 DB 训练轨迹的说明与最终答复。**

| 项目 | 前一轮 | 最新一轮 | 内容比较 |
| --- | ---: | ---: | --- |
| Add 请求 | 134 | 134 | 各对应用户的批次数、会话划分相同 |
| Add 消息 | 1,495 | 1,495 | user 1,301、assistant 194；字段形状相同 |
| 原始语料 Add | 128 | 128 | messages 逐字相同，含 role/content/timestamp；各用户批序也相同 |
| 流式反馈 Add | 6 | 6 | 4 条 QA 反馈完全相同；DB/ALF 两条轨迹存在原文差异，见下 |
| Search 请求 | 48 | 48 | 忽略运行生成的 user_id 后，全部请求体多重集相同 |
| 不同 query | 41 | 41 | 内容与出现次数相同 |
| top_k=100 | 48 | 48 | 全部相同 |
| 带 options 的 Search | 8 | 8 | 选项内容及顺序相同；其余 40 条没有 options |
| POST HTTP 200 | 182 | 182 | 未发现业务请求失败 |

**实际差异：**

- 新一轮的 user_id、request_id、session_id 全部重新生成；134 次 Add 的 request_id
  和 session_id 均与对应旧请求不同，但相同用户内部的会话划分没有变化。
- DB（task_index=289）：两轮轨迹均为 5 条记录，执行的 SQL 及工具结果相同。
  两条 assistant 说明文字不同，最终提交答案由 “has been changed to 2003” 变为
  “has been successfully changed to 2003”；tool call ID 也不同。两轮 reward/score 均为 1。
- ALF（task_index=86）：两轮轨迹均为 10 条记录，动作、参数、观察结果及说明文字相同。
  差异仅为 tool call ID 及其引用；两轮 reward/score 均为 1。
- 四条在线 QA 反馈的 predicted_answer、question 和 score 完全相同；分别为
  locomo1、locomo5、scriptMem-angry、scriptMem-enemy，score 仍为 1、1、1、0。
- 4 个用户的 query **完成记录顺序**不同，17 个用户相同。采集的 ts 在响应完成时生成，
  不能据此认定客户端发送顺序改变；这些用户的 query 内容与次数没有变化。

**比较边界：**以上结论针对平台发送的请求正文。当前采集仅保存请求、HTTP 状态与延迟，
成功的 `/search` 响应中的 data/content 未保存，因此无法直接比较两轮返回证据、
排序或命中条数。输入相同也不能证明返回内容或平台作答相同。
