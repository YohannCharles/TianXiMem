## HaluMem 与 MuSiQue 独立本地评测接入

核对日期：2026-10-06。范围：PRD §12 的本地评测加载、输入适配与评分；服务仍只接收
Add/Search 契约。数据来源和固定版本继续以 `eval/datasets/manifest.py` 为唯一清单。

### 已接入的入口

```bash
make baseline DATASET=halumem
make baseline DATASET=musique
# 服务需先启动；首次运行自动准备缺失数据及评分依赖。
# 禁止下载时加 ARGS='--offline'。
make data-check DATASET=halumem
make data-check DATASET=musique
```

`make eval DATASET=<名称>` 也可运行，默认加载全量；`make baseline` 使用
`eval/experiments/recipes.py` 声明的冻结抽样。两份都沿用当前数据目录配置与临时下载流程。

### 数据及冻结抽样的实测计数

| 数据集 | 全量独立样本 | 全量题目 | 冻结参数 | 冻结实测 |
|---|---:|---:|---|---|
| HaluMem-Medium QA | 896 个提问检查点 | 3,467 | `--limit 60 --spread` | 60 个检查点、203 题 |
| MuSiQue-Full dev | 4,834 个题目实例 | 4,834 | `--limit 120 --spread` | 120 题，可答/不可答各 60 |

HaluMem 原始文件包含 20 个用户、1,387 个会话。491 个会话没有 QA，但仍作为后续
检查点的历史保留。每个检查点的用户 ID 独立，只包含当前及此前会话，题目 ID 由用户、
会话位置、题目位置共同构造。`persona_info`、`memory_points`、题目及证据标注均不进入 Add。

检查点之间重复投喂历史是这一实现的明确成本：全量独立检查点合计投喂 1,342,018 条
消息；原始对话为 60,146 条消息。加载时共用不可变 Session/Message 对象，重复的是
实际投喂。冻结抽样覆盖全部 QA 类型，但 Dynamic Update 只有 1 题，Multi-hop Inference
只有 5 题，不能凭这个小样本判断这些类型的稳定表现。

MuSiQue-Full 同一原始 ID 出现两次：2,417 个可答变体与 2,417 个不可答变体。
两个变体分别生成用户 ID 和题目 ID，避免结果覆盖和语料混用。Add 只包含段落标题与正文，
不包含答案、`is_supporting`、问题分解链。段落顺序沿用公开文件，并非官方采集里的重采样顺序。

候选段落数并非全部为 20：20 段有 4,803 题，19 段有 17 题，18 段有 9 题，17/16 段
各 2 题，15 段有 1 题。加载器按原文逐题保留。冻结抽样按跳数及可答性分层，每种可答性
分别取 2-hop 31 题、3-hop 19 题、4-hop 10 题。

### 评分范围与兼容性

HaluMem 复用 `official_capture_pipeline.py` 中的作答入口与上游 QA 裁判：从归档的
`eval_tools.py` 读取原始 prompt，保留 Correct/Hallucination/Omission 标签，仅 Correct
计为正确；裁判解析失败保留 JUDGE_ERROR。参考回答和关键记忆点只用于裁判。
本入口不覆盖上游记忆抽取、完整性、更新指标，也不声称复现 AML 的输入适配。

MuSiQue 在 `extra_pipeline.py` 中增加本地短答案作答与纯函数评分：可答题按现有
NFKC、小写、空白及首尾包装标点归一化后精确匹配参考答案或别名；不可答题仅接受
`INSUFFICIENT_EVIDENCE`，允许首尾空白。混合答案、附带猜测或空回答不能通过拒答判分。
拒答题另通过既有 abstention 汇总记录。

MuSiQue 的独立作答入口显式带 `musique-local-qa-v1` 契约标记，旧采集重放继续使用原有
答案 prompt 与评分。这里没有实现上游 answer/support F1 或成组 sufficiency 指标，
成绩只用于相同本地口径下比较。

两份都登记了数据指纹、形状说明、正文标签和冻结抽样。HaluMem 指纹覆盖实际读取的
Medium JSONL，MuSiQue 覆盖实际读取的 Full dev JSONL；未用作 Add 的标注不生成额外数据副本。

### 输入范围

#### HybridQA

[`hybridqa.py`](../datasets/hybridqa.py) 抽题后按 `table_id` 合并，共享同一用户语料。
Add 包含整张表的标题、上下文、所有行、链接和 `request_tok` 的所有关联段落，
不会依据 `answer-node` 挑答案行/段落，不注入题目、参考答案或类别。
不合成不存在的时间戳。表格行与段落文本化是本地适配，不能假设等同 AML 序列化方式。

#### FEVEROUS

[`feverous.py`](../datasets/feverous.py) 从完整数据库构建标题及前五句 FTS5 索引。
claim 经 NFC 归一化、固定停用词过滤后 OR 查询，BM25 标题权重 8、intro 权重 1，
固定取前五页；同分按原页面 ID 排序。使用 FTS5 rank 游标提前停止，并读完最后一名的
同分行，保持与 `ORDER BY bm25(...), page` 相同的确定性边界。
[SQLite 官方文档](https://www.sqlite.org/fts5.html#sorting_by_auxiliary_function_results) 说明了 rank 游标及提前停止的排序行为。

候选生成函数只接收 claim，不接收 label、gold evidence 或 annotator 操作，漏召页面不补齐。
候选整页句子、表格、表头、caption、列表和原始元素 ID 都进入 Add；每题隔离用户，逐页分 session。
数据库原始页面/元素 ID 保留 Unicode 字节，NFC 只作用于检索 claim。

**这是有限候选整页上的本地检索评测**：完整 Wikipedia 用于固定的候选生成器，
被测 Add/Search 服务接收候选页，而非整个数据库。它不能表示被测服务在全 Wikipedia 上
的端到端检索成绩，也不复刻 AML 候选池。该范围记录在加载器版本、数据指纹和
`dataset_score.scope` 中，引用分数时必须保留。

两份作答都只读取逐题 Search 返回的 `retrieved_context`；空检索显式渲染 `(no memories)`，
不会回填原语料或 gold。默认 Add 正文使用 `Corpus:` 前缀，并沿用现有消息/词数切批。

### 评分与产物

[`corpusqa_pipeline.py`](../harness/corpusqa_pipeline.py) 下载后验证上游评分源码 sha256，
执行未改动的 import/函数节点，跳过脚本 CLI 顶层入口。回答 prompt 为本地 Search 适配。

| 数据集 | 逐题函数与结果 | `scores.dataset_score` 聚合 |
| --- | --- | --- |
| HybridQA | 上游 `compute_exact`、`compute_f1`；`is_correct` 对应 EM | `exact_match`、token `f1` 的逐题均值，`mean` 为 EM |
| FEVEROUS | 上游 `truncate_evidence`、`is_correct_label`、`is_strictly_correct`、`evidence_macro_precision`、`evidence_macro_recall` | `strict_score`、`label_accuracy`、证据 macro precision/recall 和二者的调和 `evidence_f1`；`mean` 为严格分 |

FEVEROUS 回答 JSON 为 `label` 加元素 ID 列表，只接受 Search 文本中可见的 ID。
元素 ID 从结尾的类型/位置解析，页面名可以含下划线；转换为上游 `[page, type, position]`。
按上游最多五条句子及二十五条其他元素截断。
标签正确且至少一个金标证据组被完整覆盖才得严格分，**NOT ENOUGH INFO 同样执行该上游规则**。
非法 JSON/标签/证据或引用不可见 ID 记 `ANSWER_ERROR`，所有逐题指标为零。

上游聚合函数在平均 precision 和 recall 同为零时会除零；本仓复用逐题函数，聚合时将
该调和 F1 定义为零，不修改上游源码。证据 F1 是**先平均 precision/recall 再取调和均值**，
不是平均逐题 F1。`overall` 保持二值 EM 或严格正确率，额外指标经
`JudgeResult.metrics` 汇总并打印在 CLI 和 run record 中。

答案文件包含完整输入指纹；同一 run-id 的 Search 结果或其他输入变化时，在发起模型请求前
拒绝复用旧答案。evaluate 先核对全部 ID 和输入指纹，再打开判分产物。
官方采集重放继续执行原有 label-only FEVEROUS 口径，不能与本次严格证据组分混用。

### 冻结抽样与复现

参数的唯一声明处为 [`recipes.py`](../experiments/recipes.py)，`--frozen` 不与显式 limit/spread 混用。

所有用户的初始检查点在首次 HTTP 前建立；删除用户目录、丢失历史快照或改变输入/执行配置会明确失败。

#### 与 Full 的实际差距

- **时间与批界**：合成时钟冻结了形态，不猜测平台用户偏移。8,000 字符切片与 20 条/2,000
  空白词切批是本地近似；逐请求字节一致仍依靠原始采集回放。
- **MQuAKE**：一公开 case 一用户，是有序更新测试的小语料范围；不是捕获中按用户聚集的大事实池。
- **LoCoMo**：每个完整对话配一个确定性公共 LME haystack。公开题库没有逐题到达时刻和平台反馈，

- **HaluMem/MedMemoryBench**：保证公开已选检查点的历史可见性，但不能声称检查点到达顺序与具体平台
  调度完全一致。`max_questions` 在合并前按源检查点/QA 子集裁题，不代表每个合并用户的总题数上限。
- **FEVEROUS**：本地捕获 Add 恢复出 416 个页面标题，再从公开数据库加载原始页面。
  DB 中存在 NFD 标题、清单中存在 NFC 标题，查询兼容二者，实际 JSON/引用保留源页面拼写。
  重新序列化与切批后为 993 Add/2,267 消息，与捕获的 1,112 Add/2,500 消息不逐字相同。
  默认 claim 子集按同一捕获的原始 query 唯一匹配到公开 dev，保留原始 Search query；
  重复请求合并，公开标注用于评分。显式自定义池的公开全集选题则是另一来源范围。
  严格证据分依赖 Search 实际返回完整可解析页面或显式 ID；
  残片无法补全，可能产生标签正确但严格分为零的结果。
- **评分**：其余适配器继续复用各自已有本地答案/评分入口，FEVEROUS 仍为标签与完整证据组评分；
  它不同于采集重放的 label-only，不等同 AML 平台最终分数。
- **未支持**：TempReason 与 LongMemEval 独立 QA 缺少可靠的捕获实例映射，`aml-v1` 明确拒绝。
  原生入口继续可用；LongMemEval 语料作为 LoCoMo 干扰历史使用。BEAM、CL-Bench、PersonaMem 等
  未登记此版适配器的家族同样明确拒绝，不静默回落。

#### 最值得先改的几项

##### MQuAKE：现在没有测到同一份更新任务

Native [mquake.py](../datasets/mquake.py) 的 `_memory_messages` 会同时注入原始事实与自然语言改写，
`_questions` 一律取更新后答案。在已恢复金标的 Full 查询中，386 条对应原始状态，738 条对应更新后状态；
249 个相关 user 中 126 个在首次 Search 后仍有 Add。不能把本地全部更新后的结果当成两阶段测试结果。

兼容臂应从相同公开 case 构造带 ID 的事实 JSON，保留明确的 UPDATE 包装，并在同一 user 上分两阶段提问。
若只把 natural language 前面加 `Corpus:`，这几个差异都还存在。

##### FEVEROUS：语料池、检索范围和 query 同时不同

把 2,500 条采集消息的 `Corpus:` 包装去掉，按原顺序拼接后，可以完整解析出 **416 个 JSON 页面**，
其标题均不重复，总正文 16,442,322 字符。1112 次 Add 后才开始该 user 的 249 次 Search。
这与 [feverous.py](../datasets/feverous.py) 的每题 top-5 页输入有不同的干扰范围及召回前提。

下载了完整 Wikipedia SQLite 并不能使二者自动相同：当前 native 先用 claim-only FTS/BM25 选页，
被测服务仅看选中的五页。应增加共享语料池/原始 JSON 的测试口径，或者直接回放捕获的 Full 输入。
共享池应从声明的输入来源生成，不能从问题的 gold evidence 补页。

Search 的核查指令也需要保留：Full 明确要求三类标签及原生证据 ID；
native 虽在答案 prompt 中提出标签/证据要求，但该 prompt 没有被送入 Search。

##### LoCoMo：同题不同记忆库

Full 中归到 LoCoMo 的 user 内，36,566 条消息使用 `User:`/`Assistant:` 标签；
其中 **36,510 条正文**能在公开 LongMemEval-S 的消息里精确匹配。
这证明了源语料交叉，不能只用数据集名称或题面匹配来判断 Add 已对齐。

该族还有全 user 的真人对话输入，当前 native `official` 保留 assistant。
此外，8 个有 LoCoMo 查询且有 Add 的 user 在首次 Search 后仍有 Add。
单纯「完整原始对话先 Add、然后问全部题」无法复现上述状态，适合用真实请求的 timeline 回放作对照。

##### 时间、会话边界：不应通过删掉历史来修

Full 的 HaluMem、MedMemoryBench 分别有 7、3 个相关 user 出现交错。
Native 的独立检查点方式避免使用后续会话，原则合理；与持续 user 的索引演化仍不等价。
应补持续更新的验证，不应改成先投喂整个未来历史再问早期问题。

CorporateBench 则是一个可以低成本对齐的例子：消息本身完全一致，Full 的 353 次单消息 Add/353 个 session
与本地单 session 合批不同。批界和 session 会影响配对、邻接及段合并；ID 字面值可以不同，作用域应该明确。

#### 建议的实现方式

1. **保留当前原生 pipeline 作为基线，增加显式的输入契约版本。** 对照运行的 manifest 记录语料构造、
   query 包装、timestamp 形态与批次口径；输入变更使用新的 run ID、存储及配置快照。
2. **将检索 query 与答题题干分开。** 当前只有 `Question.question`，同时服务于 Search 和作答。
   可新增可选 `search_query`，缺省仍用题干；MuSiQue 和 FEVEROUS 的兼容口径填完整 Full query。
3. **分别增加 JSON/时序输入适配。** 优先处理 MQuAKE 两阶段更新、FEVEROUS 共享页面池和 LoCoMo 干扰/timeline；
   然后对齐 HybridQA JSON、CorporateBench 会话边界及对话数据的时间包装。MuSiQue 包装可作为较小改动先落地。
4. **用已有 [official-capture replay](../experiments/replay_official.py) 检验原始 Full 输入。**
   它绕过 `add_shape`/重新切批，在 user 内按采集 timeline 投递原文 Add 和完整 query，适合作为输入对齐主线。

全局并发和平台实际重试不能由当前串行重放完整还原。它复现的是已有请求输入及已记录的时序。

**输入对齐也不代表评分对齐。** 多份本地 answer/judge 是自写适配。

### 四、修订方案：现有 pipeline 上的 P1–P3

代码/配置改动通过现有 HTTP runner 评分；测试一个局部改动不需要先完成官方重放。

#### P1：有效状态与现有来源的取证覆盖

**P1a：状态更新。** 先解决明确更正与当前状态，涉及 D1/D2/C3/E1 的能力假设：

- 在共同记录及派生索引中表达声明主体、属性、范围、有效区间、明确替换关系及逐字来源。
- 当前状态问题优先保留有效值支持片段；历史时间问题仍保留其适用的旧值来源。
  未声明替换的冲突保留双方，未知顺序不猜新值，不以最后到达一律覆盖。
- 共同取证与混合检索回表、邻域、打包遵守相同状态规则，避免一条路径筛掉的无效值从另一条重新出现。
  状态规则依查询范围生效，不把历史原文永久当作无效记录删除。
- 开发验证覆盖明确更正、历史查询、幂等重投、乱序及引用中的更正句。
  先跑 MQuAKE、LongMemEval、MedMemoryBench，再用 TempReason 与 MemTrap 检查时间及冲突行为。
  不改 native MQuAKE 的问题/金标去制造更新前评分，否则需要独立新口径。

删除/永久擦除及复杂披露策略从本轮功能主线移出。若状态实现涉及明确撤回，
只对有可靠行为用例的语义做实现和回归；没有对应评分时不宣称 D3/H2 已改善。

**P1b：取证覆盖。** 优先改善实际 native 文本来源与集合证据：

- 针对可读三元组、显式自然语言改写、邮件字段、时段、表格标题/表头/单元格及链接段落关联，
  扩充按共同结构定义的确定性规则；不按数据集名、qid、题面或 gold 在产品中分支。
- 逐字引句及来源范围必须可核对；碎片、未知关系及不完整范围回原混合检索。
  名单/计数只返回独立证据，不在 Search 中计算答案（PRD §2.1、D33）。
- 随改动补计划适用、事实/原文投影、未覆盖来源、未解释声明、冲突、超限等诊断。
  诊断直接随本轮 pipeline 落盘，不另设官方对照阶段。
- 先跑 CorporateBench、TempReason、HybridQA、FEVEROUS。仅在诊断证明上限是实际原因时，
  才做 `evidence_limit` 的单变量对照；保持完整性判据与双预算。
  官方 JSON 三元组及 UPDATE 包装留到能单独验证该输入时再做。

#### P2：多证据选择、顺序与覆盖

主验证用 MuSiQue、LongMemEval、LoCoMo、MedMemoryBench、HybridQA、FEVEROUS；
CorporateBench、MQuAKE、TempReason 用作已有优势的回归。

1. 从现有失败结果核对源文本、候选、返回与模型输入，判断必要证据丢在何处。
   不仅凭错答或裁判判词认定检索失败。
2. 固定候选池先比较一次 rerank 开/关，再单独比较去重、来源覆盖或片段组织。
   候选规模、Add 输入、答案预算、模型和评分器保持一致；不把多个改动一起归因。
3. 保留多跳连接点与各段支持来源，让长历史覆盖不同事件阶段，避免相似复述占满位置。
   日期、说话人、表头及文档身份跟随来源，各独立片段自定界，跨 Add 不伪造连续对话。
4. 最终仍按既定双预算按段输出；改变已锁定顺序/选择语义时同步设计决定。
   Add 不生成 LLM 摘要，Search 不生成答案（PRD §7.2、§2.1）。

MuSiQue 同时报可答准确率与不可答拒答结果，FEVEROUS 同时报标签、严格证据组和证据指标；
HybridQA 同时报 EM/F1。指标拆分用于判读原有评分，不冒充 AML 维度成绩。

少量正确来源 oracle 可用于诊断，答案 prompt 与裁判固定，gold 只在诊断选源中出现。
正确来源仍无法作答的案例要单列模型上限，避免无依据扩大上下文或继续重复检索。
F1 的本轮代理验证仅限已有长历史问题，不把 LongMemEval 总分当作全局摘要专项分。

#### P3：偏好、个人背景与误用控制

本轮缩为现有 QA 能覆盖的 E1/E3 及证据误用控制：

- 保留个人声明者、偏好的否定/例外、有效状态与相关背景，区分用户声明、助手建议和被引用内容。
- 用 HaluMem、MedMemoryBench、LongMemEval 验证；HaluMem 同时报 Correct/Hallucination/Omission。
  LoCoMo 和 MemTrap 作为来源/冲突/负迁移回归，不把 `role` 一律当作真人身份。
- 若需要更强个性化专项，可使用已有 PersonaMem-v2 pipeline；
  先补 `_build_personamem_items` 的答案 token 前缀截断，再建立修复后同口径基线。
  这是已有第十二份入口的补充验证，旧完整历史分不可复用，也不混入当前十一份历史主表。
- H2 条件披露、G3/G4 工作流/模拟、I1/I2 在线反馈完整专项暂缓。
  CL-Bench/BEAM 的旧基础设施阻断未解决时不加入必跑队列；ScriptMem/Doc-PP 采集重放也不进入本轮。

没有相应端到端指标的能力只能报告“本轮未覆盖”。用户隔离、Add 幂等、原文来源和显式冲突等
已有正确性约束仍按代码改动范围回归，不因暂缓某项评分而放宽。

### 五、跑批顺序与采纳条件

1. **现有失败题开发验证。** 从已保存 native 结果中固定失败案例和正确对照，保留题号及完整原始语料；
   每次产品改动按新增行为补必要测试，再通过 HTTP runner 做少量端到端冒烟。
   这属于 P1–P3 各阶段的验证，不增加官方对照前置工作。
2. **按阶段跑关联数据集。** 使用各自 `--frozen` 配方；原十一份选题仍为 3,001 题，
   不为了方便把所有数据集 `--limit` 设成同一个数。失败题开发结果不冒充完整子集结果。
3. **留出验证及最终回归。** 开发案例之外保留未用于调参的问题/场景；候选方案过留出验证后，
   最终串行重跑全部十一份冻结子集，比较当前完整历史参照并保留逐题赢/输。
   接近噪声的小幅变化需要复核，不能只挑已知失败题报涨幅。
4. **冻结实际输入与模型。** 代码、配置、数据、题号、Add 形态、模型及 prompt 留指纹，
   每阶段使用新 run-id。变更影响持久化派生数据时独立建库/重建，不沿用旧索引或旧答案缓存。
   纯排序对照可复用已核对一致的原文库与候选，语料与 scorer 不变。
5. **串行跑，错误不删题。** 网关现有限制下只跑一条回答/判分链。保留回答/裁判错误，
   技术故障修订单独登记，不靠删除失败题或改判分制造产品收益。
6. **采纳端到端改善。** 在关联数据集与留出验证上有可复现收益，最终回归无明确系统性退化；
   原文引句、有效状态、范围完整性、用户隔离、幂等及 `top_k=100` 等不变式通过。
   本轮只报原指标及覆盖范围，不估算九维平台分或新版 Full 总分。

推荐的实际次序是：**P1a 状态更新 → P1b native 取证覆盖 → P2 多证据组织 → P3 偏好与误用控制**。
每阶段先跑关联数据集，最后汇总十一份；官方输入对照与目标提交模型复核保留为之后的独立任务。

### 五、数据集结构及字段说明

**格式**：JSONL，**一行 = 一个用户**（`HaluMem-Medium.jsonl`，20 行）。

```
uuid ─┬─ persona_info (str)          # 用户画像文本，[Recorded on ...] 开头，均值 140 token
      ├─ sessions[]  ← 一行一个 uuid，含全部 58–82 个 session
      │    ├─ start_time / end_time     # "Sep 04, 2025, 18:42:18"（session 级，含秒）
      │    ├─ dialogue_turn_num          # 轮对数量
      │    ├─ dialogue[]                 # [{role, content, timestamp, dialogue_turn}]
      │    ├─ dialogue_token_length      # = o200k(dialogue 各 content) —— 已验证
      │    ├─ memory_points[]            # 该 session 抽取的记忆点（数据集标注，非检索产物）
      │    │    └─ {index, memory_content, memory_type, memory_source,
      │    │        is_update, original_memories[], importance, timestamp}
      │    └─ questions[]                # 该检查点的评测题（0–15 条）
      │         └─ {question, answer, evidence[], difficulty, question_type}
      ├─ total_dialogue_token_length
      ├─ total_question_count
      └─ token_cost
```

**组织关系与关联**

- **用户 → Session → Message**：`uuid` 下 `sessions` 数组有序，每个 session 的 `dialogue` 按 `dialogue_turn` 成对（user + assistant）。
- **时间戳**：message 级（`timestamp`，“Sep 04, 2025, 18:42:18”，**秒级**）、session 级（`start_time`/`end_time`）、记忆点级（`timestamp`）、数据集级（`persona_info` 里的 `[Recorded on Oct 04, 2025]`）。
- **标准答案**：`questions[].answer` 是**自由文本**（含 "Unknown; not provided by the user." 这类拒答）。HaluMem 的裁判走 **QA 三分类**（见 [`eval/datasets/CLAUDE.md`](../datasets/CLAUDE.md)）。
- **证据定位**：`questions[].evidence[]` 列 `{memory_content, memory_type}`——**指向记忆点，不是指向对话轮**；Memory Boundary 的 evidence 恒为空数组。
- **记忆点标注**：`memory_source` ∈ {primary, secondary, interference, system}；`is_update: "True"` 的记忆点用 `original_memories` 指回被覆盖的旧记忆（**字符串 "True"/"False"**，不是布尔）。

**重复与去重**

| 层面 | 是否重复 | 去重方式 |
| --- | --- | --- |
| Session（含正文） | **无**（1,387 唯一） | 不需要 |
| 消息 content | 有（60,146 条中 10,545 条重复） | 按 `content` 去重 → token 3,198,219 → **2,661,107** |
| 评测 question 文本 | 有（278 条重复） | 按 question 文本去重 → 3,467 → **3,189** |
| 投喂前缀 | **大量重复**（22×） | 加载器设计如此；embedding 缓存按内容哈希 ⇒ 不重付钱 |

### 六、简短总结

- **规模**：20 用户 / 1,387 session / 3,467 道评测题 / **320 万 token**；单用户上下文约 **16 万 token**（与官方 "~160k" 一致）。
- **主要考察的记忆能力**：以 **记忆边界 / 幻觉抑制（23.9%）** 与 **冲突、事实召回、泛化（各约 21.5–22.2%）** 为主，真正的多跳推理与动态更新合计仅 **10.9%**。
- **最突出的评测特点**：
  1. **操作级幻觉评测**——题目直接对应记忆系统的三步操作（抽取 / 更新 / 问答），每道题都挂 `evidence` 记忆点，可定位到"错在哪一步"；
  2. **拒答是最大单一题型**（828 题，evidence 全空），考的是**不乱答**；
  3. **干扰记忆内建**——`memory_source: interference` 的记忆点是数据集主动埋的对抗噪声（2,648 条）；
  4. **检查点式投喂**——同一段历史会在后续检查点被反复喂入（22×），评测展开规模远大于原始正文规模，**统计时必须区分两者**。

### 五、数据集结构及字段说明

**格式**：3 个部分，**题目/金标是 JSON 数组/对象，语料是 per-table 的 JSON 文件树**。

```
dev.json                  JSON 数组，3,466 条
  [ {question_id, question, table_id, answer-text, question_postag}, … ]

dev_reference.json        一个 dict，三个键必须成对校验（加载器强制）
  { "reference": {question_id: 答案串},     ← 3,466 条，单独的真源
    "table":     [question_id, …],          ← 1,349，官方评测分组
    "passage":   [question_id, …] }         ← 2,025，与 table 互斥

tables_tok/{table_id}.json    整表（结构化，未文本化）
  { "title": str, "header": [[text, [links]], …], "data": [[[text,[links]], …], …],
    "intro"?, "section_title"?, "section_text"? }

request_tok/{table_id}.json   该表的全部超链接段落
  { "/wiki/Page_Name": "段落正文", … }      ← 3,053 个文件，共 101,753 段

corpus-manifest.json          语料收据（sha256 + archive_sha256）——⚠ 本地缺失
```

**组织关系与关联**

- **表 → 问题是一对多（3,053 : 3,466，最多 1:4）**；**问题 → 表是严格一对一**。加载器**按 `table_id` 分组**：同一张表的题共享同一段 `Add` 语料 ⇒ 语料只投喂一次（这解释了为什么"500 题"这类说法在 HybridQA 上等于"305 张表"）。
- **`table_id` → `user_id`**：`"hybridqa-" + sha256(table_id)[:20]`——**表即用户**，题**不**进 `user_id`。这与 LoCoMo/LME 的"题即用户"完全不同。
- **时间戳**：⚠ **完全没有**。题目、金标、表格、段落**都没有任何时间字段**（加载器也不合成）。
- **标准答案**：`dev_reference.json` 的 `reference[qid]` 是**单个字符串**，与 `dev.json` 的 `answer-text` **必须逐字一致**（加载器对此硬校验，不一致即 `ValueError`）。**答案是极短的抽取式span**——均值 **12.3 字符 / 2.1 词**（最长 109 字符）。
- **证据定位**：⚠ **没有 `evidence` 字段**。定位信息**隐含在超链接里**——单元格 `(links: /wiki/X)` 与段落键 `/wiki/X` 对应，但**加载器刻意不读 answer-node、不挑答案行/段落、不注入题目或答案**（见模块 docstring）。**因此无法做证据级 oracle 诊断**。
- **判分口径**：**上游固定版本的 `evaluate_script.py`**（在 `dataset/.upstream/hybridqa/`）：`normalize_answer` 做小写 + 去冠词 + 去标点 + 折空白，再算 **EM** 与 **token-F1**；分组报 `table/passage` 两组，外加 `total`。

**重复与去重**

| 层面 | 是否重复 | 去重方式 |
| --- | --- | --- |
| `question` 文本 | **无**（3,466 唯一） | 不需要 |
| 答案串 | 少量（2,976 唯一 / 3,466，重 490） | 短答案天然重名（`3`、`2`、`Yes`），**不是数据问题** |
| `table_id` → 用户 | **无重复**；一表多题是**分组共享**，不是重复投喂 | 按 `table_id` 分组即可 |
| 段落正文 | **有**（101,753 段 → 73,071 唯一），**28,682 段跨表重复** | 按正文去重 → token 26,127,222 → **18,841,804** |
| `tables_tok` / `request_tok` 文件名 | 31 个含 `:`（Windows 非法） | 加载器 `safe_table_id()` 只挡 `/\` 与 `..`，**不挡 `:`** ⇒ **依赖 `make fetch-data` 的发布层处理**，见下 |

---

### 六、简短总结

- **规模**：**3,466** 题 / **3,053** 张表（= 用户） / **153,290** 条语料消息 / **2,613 万 token**；单表均值 **8,558 token**（中位 7,496，1,150–47,720）。**零前缀展开**——题与表一一绑定，原始规模 = 投喂规模。
- **主要考察的记忆能力**：**异构多跳**——在"结构化表格 + 非结构化百科段落"两种形态之间做实体消解、聚合与比较。官方把题分成 `passage`（58.4%）/ `table`（38.9%）/ 未分类（2.7%）三组，仅用于**分数拆分**，**没有**任何语义或难度标注。
- **最突出的评测特点**：
  1. **上下文全是噪声**——一题拿到整张表 + 全部 33 个（最多 209 个）链接段落，**加载器不挑证据、不给提示**，考的是"从 50 条消息里自己找出那 1–2 段"；
  2. **表即用户**——`user_id = sha256(table_id)`，一表多题共享同一份 `Add` 语料（3,053 用户 : 3,466 题），**不是 3,466 个用户**；
  3. **抽取式短答案 + 官方 EM/F1**——答案均值仅 2.1 词，判分复刻上游固定版本函数，**口径稳定**，是本仓少见的"非 LLM 裁判"评测；
  4. **无时间戳、无证据字段、无 assistant 消息**——无法做时间推理、无法做证据 oracle、语料全部渲染成 `role: user`；
  5. **⚠ 本地语料尚未就绪**——`tables_tok/` 未解、`request_tok/` 只有 620/3,053、`corpus-manifest.json` 缺失，**当前跑不了**，须先 `make fetch-data hybridqa`；本报告的数字是从 tar 包按需抽取全部 6,106 个语料文件后重算的。

### 五、数据集结构及字段说明

**格式**：6 个 Parquet 文件，均为**长表**（一行一记录），通过 `persona_id` / `session_id` / `event_id` / `query_id` 关联。

```
personas.parquet     20 行 —— persona_id, type_name, gender, category, core_feature,
                                 health_goals, age_range, occupation_detail, background_story,
                                 sleep_pattern, diet_habits, exercise_frequency, stress_level,
                                 medical_history, disease_progression
      │
      ├─ events.parquet        2,074 行 [persona_id, event_id, event{text}, type, event_date, triggered_by]
      ├─ trap_events.parquet     120 行 —— 120 = 20 persona × 6 类安全事件（allergy / medication_history /
      │                                      disease_history / medication_preference / diet_preference /
      │                                      lifestyle_economic）
      ├─ dialogues.parquet    31,976 行 —— 一行一消息
      │      [persona_id, session_id(1–101), turn, role(user=患者/assistant=医生),
      │       content, agent_type(user_agent/doctor_agent), event_id,
      │       event_info(JSON:{event,type,date}), knowledge_points(JSON[]), kp_count, turn_count]
      ├─ clinical_reports.parquet 20 行 —— phase_1..phase_5 五阶段临床报告（长文本）
      └─ queries.parquet       1,939 行 —— 一行一评测题
             [persona_id, query_id, session_id(检查点,10 的倍数), query_type,
              question, answers(JSON[]), source_key_points(JSON[]), metadata(JSON)]
```

**组织关系与关联**

- **用户 → Session → Message**：`(persona_id, session_id)` 唯一确定一次问诊；`turn` 是 session 内轮次。**一次问诊共享一个 `event_info`**（同一天、同一事件），故 **session 内没有时间区分度**（与 LoCoMo / LongMemEval 同形，§6.1）。
- **时间戳**：`event_info.date`（`YYYY-MM-DD`，session 级）；`trap_events.event_date`；知识点 `time`（可空，本数据里出现过字符串 `"None"`）。
- **标准答案**：`answers` 是 JSON 数组，每条 `{content, is_correct, explanation}`——**`is_correct` 是 gold 的标记，不是模型答案**。全库 1,939 题共 **3,133 条** gold 答案，其中 **2,263 条** `is_correct: true`。⚠ **选择题（`multiple_choice`）的 `answers` 把全部 4 个选项都列出**（该类型 1,592 条答案里只有 **722 条**为 true，即平均每题 1.8 条"正确"文本），判分须按 `metadata.correct_count` 区分，**不能用"答案条数 = 1"假设**。
- **证据定位**：`source_key_points` 是知识点数组 `{category, name, content, trap_score, time, session_id}`——**`session_id` 指回具体问诊**，这是 `state_update`（均值 29 条）与 `multi_hop` 的关键。
- **难度与陷阱**：`metadata.difficulty`；MCQ 的 `metadata.trap_design`（`trap_type` / `trap_mechanism` / `why_others_fail` / `required_patient_info`）；Multi-hop 的 `metadata.reasoning_chain` / `sessions_involved` / `time_span_days`。

**重复与去重**

| 层面 | 是否重复 | 说明 |
| --- | --- | --- |
| 消息 `content` | **无**（31,976 唯一） | token 去重前后同为 **13,860,137** |
| 评测 question 文本 | 1 条重复 | 1,939 → 1,938 |
| `knowledge_points` | **高度累积** | ⚠ `kp_count` 随 `session_id` **单调递增**（persona 1：session 1 = 8 → session 101 = 256），即每行携带的是**到该次问诊为止的累计知识点**，不是本次新增。统计时按 session 取一次，勿逐 turn 累加 |
| 投喂前缀 | **重复**（5.33×） | 加载器检查点设计的固有代价 |

### 六、简短总结

- **规模**：20 患者 × 101 次问诊 = 2,020 session / 31,976 条消息 / 1,939 道题 / **1,386 万 token**；单患者 12 个月病程约 **69 万 token**，单题前缀约 **37 万 token**。
- **主要考察的记忆能力**：**单条事实检索与时间定位合计占 39.9%**（774 题），是最轻的一端；**状态更新追踪（10.1%）与多跳临床推理（9.8%）** 是最重的两端，前者要跨 18 个 session 翻用药史，后者要串 2–4 个病例节点。难度自报 **hard 占 64.8%**。
- **最突出的评测特点**：
  1. **检查点式时序评测**——每次问诊后提问"到此刻为止"的记忆，`session_id` 是 10 的倍数，**天然禁止读未来**；
  2. **医疗安全陷阱内建**——120 条 `trap_events` + 每题 `trap_design`，考的是"记得住 + 不出危险建议"；
  3. **原始正文零重复、展开 5.33×**——统计原始规模与投喂量必须分开；
  4. **对照强**——中英双语对齐、`events.parquet` 提供 2,074 条因果事件时间线（`triggered_by` 建因果图），可做"证据在不在"的 oracle 诊断。

| 种子文件字段 | — | `inertia_seed.json`：`DOMAIN`/`SEED_ID`/`STRATEGY_A`/`STRATEGY_B`；`hurt.json`：只有 `domain`/`id` | **163 条，加载器跳过并报数** |

**组织关系与关联**

- **用户 / Session / Message / QA 四者在本数据集里是 1:1:1:1**——一条样本 = 一个独立 `user_id` = 一段 `context_history`（1 个 session）= 1 道 `final_trigger`。**没有跨样本的用户或 session 共享**。
- **时间戳**：⚠ **完全没有**。`context_history` 的每条消息只有 `turn` / `role` / `content`，**没有时间字段**。加载器据此把 `event_time` 置 NULL、`created_at` 发空串（§11.3 的有定义降级路径）——**不是漏读**。
- **标准答案关联**：`gold_standard` 与 `final_trigger` 成对；`expected_failure_output` 与 `gold_standard` 构成"错/对"两极。**判分口径是我们自定的**（官方只给四维均分，无过/不过线，见 loader docstring）。
- **证据定位**：⚠ **没有 evidence 字段**——这是本数据集与其他几份最大的结构差异，无法做"证据在不在"的 oracle 诊断。

**重复与去重**

| 层面 | 是否重复 | 说明 |
| --- | --- | --- |
| `context_history` 整段 | **无**（1,050 唯一） | 无需去重 |
| `final_trigger` | **无** | — |
| 消息 `content` | 少量（4,565,520 → 4,453,884 token，重复 2.4%） | 跨样本的模板句 |
| 前缀/检查点展开 | **无** | **1 样本只喂 1 段对话**，原始规模 = 投喂规模 |
| 子类型字符串 | **大量近重复** | `interference_type` 等自由文本字段需归一化后才能统计 |

### 六、简短总结

- **规模**：**1,050** 条样本 / 1,050 个独立用户 / 1,050 段对话 / **456.6 万 token**；单条对话均值 **4,348 token**（中位 3,266，654–32,472）——是**本仓最轻量**的评测集，但**陷阱密度最高**。
- **主要考察的记忆能力**：**不是"记得住"，而是"何时不该用记忆"**。四类陷阱里 81.0% 属 Reasoning Fixation（任务边界 / 认知偏置 / 创伤，共 850 题），19.0% 属 Belief Distortion（安全，200 题）。
- **最突出的评测特点**：
  1. **记忆有害性评测**——官方质检强制 `final_trigger` **无历史也能答对**，因此分数直接度量"历史把模型带偏了多少"，方向与本仓其他数据集**相反**；
  2. **1:1:1:1 结构**——一题一段对话、零共享、零展开，统计口径最简单，**不存在原始/展开规模的分歧**；
  3. **红队数据内建**——`expected_failure_output` 100% 覆盖，`test_type` 分 red/green，可直接做"踩坑率"诊断；
  4. **无时间戳、无 evidence**——不能做时间推理评测，也不能做证据级 oracle 诊断；且**子类型标签多为自由文本**，只有 `poison_type`（3 值）与 `test_type`（2 值）是可统计的受控标签；
  5. **方差极大**——中位数（3,266）与均值（4,348）差 33%，`number_game_200` 单文件仅 659 token，与其他场景相差近 20 倍。
