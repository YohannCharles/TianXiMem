# V1.0 AML Full 与当前共同取证版本的优化路线（2026-10-06）

本报告回答下一轮优先改哪些 Add/Search 能力。V1.0 平台成绩来自用户提供的 Full 报告；
当前本地成绩来自 [十一数据集汇总](eleven-datasets-scores-20261006.md)。

**执行方案已按用户后续指示修订**：本轮使用现有十一份原生数据集 pipeline，
官方输入对照移出计划。第四、五节为当前执行方案，第三节的采集审计仅保留为背景。
原方案的删除/隐私/流程/流式专项按现有评测覆盖收窄，未覆盖能力暂缓验收。
本次仅核对代码、报告及此前离线审计；本轮改动为规划文档，没有启动新跑分或实施产品改动。

编译出计划不代表抽取到了事实、完整性审查通过、实际走共同取证或回答正确。
原七数据集审计只记录单条事实返回命中数，原文投影没有计入该数；不能由它估计整个分支覆盖率。
应补充适用计划、来源覆盖、成功投影及回退原因的诊断记录，再决定扩大哪一种通用句法。

当前源码还有四个与路线直接相关的边界：

1. `grammar.py` 的一种关系边入口只接受短单行自然语言，未形成通用 JSON 三元组抽取入口。
   AML 的 MQuAKE 则有带实体/关系 ID 的 JSON 与 UPDATE；来源句法应扩展并逐字校验引句。
2. `retrieve/evidence.py::_current` 识别有限显式替换，`_quantities` 对数量做保守新旧消歧，
   不等于通用属性版本、删除/抑制与披露策略；`QueryPlan("current")` 是当前题面输入完备判定，
   不是“返回最新有效状态”。
3. `evidence_limit` 当前为 12；超限整条回退，物理索引扫描完也不代表语义集合完整。
   大集合失败应记录上限原因，满足完整性及预算条件后再做单变量上限对照。
4. 原始采集只有请求及部分反馈，没有 V1.0 当时的 Search 返回证据。
   `replay_official.py` 现有缓存续跑没有与 `plan_driver.py` 相同强度的历史状态/指纹检查，
   已推进到后期的库上补早期 Search 有未来泄漏风险；这是一项源码检查结论，未据此宣布任何已有跑分作废。

## 四、修订方案：现有 pipeline 上的 P1–P3

本轮固定 `--input-contract native`，沿用原十一份的加载器、Add 形态、切批、
答案提示词及原评分入口。共同取证保留开启，模型仍用原本地开发配置。
正式子集由 `FROZEN_RECIPES` 与 `--frozen` 冻结，不混入 `aml-v1` 或采集重放成绩。
代码/配置改动通过现有 HTTP runner 评分；测试一个局部改动不需要先完成官方重放。

### 能否直接跑及其覆盖边界

| 项目 | 现有验证入口 | 能否直接验证 |
| --- | --- | --- |
| 当前有效状态、明确更正 | MQuAKE 的原事实 + 自然语言改写；LongMemEval knowledge-update；MedMemoryBench state_update | 可以做同输入前后评分。native MQuAKE 只问更新后状态，不验证更新前 Search 或交错反馈 |
| 结构化字段、集合与时段 | CorporateBench、TempReason、HybridQA、FEVEROUS | 可以直接评分；保持已有候选池与上游指标 |
| 多跳、跨会话、长历史证据组织 | MuSiQue、LoCoMo、LongMemEval、MedMemoryBench、HybridQA、FEVEROUS | 可以直接评分；缺正确来源与模型没用好来源需要逐题区分 |
| 偏好、个人背景及来源归属 | HaluMem、MedMemoryBench、LongMemEval 的偏好题，MemTrapBench 作回归 | 可以验证当前 QA 效果，不等于完整个性化/安全分 |
| PersonaMem 检索选择题 | 已有适配器，不在当前十一份里 | 可作为后续现有 pipeline 专项；先补答案 token 前缀预算，再建新基线 |
| 删除/遗忘、同用户条件披露 | 当前十一份没有完整专项判分 | 本轮暂缓成绩验收；开发所需小型行为测试单独登记，不充当数据集分数 |
| 程序/流程、经验模拟 | CL-Bench、BEAM 有入口；ScriptMem 无独立完整公开语料入口 | CL-Bench/BEAM 旧跑批被本机长上下文网关限制阻断，本轮不列为必跑 |
| 在线反馈与内部迁移 | native runner 按样本先 Add 后 Search；HaluMem/MedMemoryBench 使用独立检查点 | 本轮不完整覆盖 I1/I2；完整闭环需另有事件用例，不能从检查点 QA 得分宣称验证 |
| JSON 三元组、官方 UPDATE 包装 | native MQuAKE 使用可读三元组与自然语言改写 | 原方案的额外 JSON 输入扩展暂缓；现有十一份不足以验收该新输入路径 |

上述可运行性依据现有加载器、runner 和评分分派核对。十一份已有完整子集产物，但
MemTrap/FEVEROUS 的技术失败仍保留在原分母内；有运行入口不保证每道远端请求无故障。
这里没有新发模型请求验证网关当前可用性。

### P1：有效状态与现有来源的取证覆盖

**P1a：状态更新。** 先解决明确更正与当前状态，涉及 D1/D2/C3/E1 的能力假设：

- 在共同记录及派生索引中表达声明主体、属性、范围、有效区间、明确替换关系及逐字来源。
- 当前状态问题优先保留有效值支持片段；历史时间问题仍保留其适用的旧值来源。
  未声明替换的冲突保留双方，未知顺序不猜新值，不以最后到达一律覆盖。
- 共同取证与混合检索回表、邻域、打包遵守相同状态规则，避免一条路径筛掉的无效值从另一条重新出现。
  状态规则依查询范围生效，不把历史原文永久当作无效记录删除。
- 开发验证覆盖明确更正、历史查询、幂等重投、乱序及引用中的更正句。
  先跑 MQuAKE、LongMemEval、MedMemoryBench，再用 TempReason 与 MemTrap 检查时间及冲突行为。
  不改 native MQuAKE 的问题/金标去制造更新前评分，否则需要独立新口径。

删除/永久擦除及复杂披露策略从本轮功能主线移出。若状态实现涉及明确撤回，
只对有可靠行为用例的语义做实现和回归；没有对应评分时不宣称 D3/H2 已改善。

**P1b：取证覆盖。** 优先改善实际 native 文本来源与集合证据：

- 针对可读三元组、显式自然语言改写、邮件字段、时段、表格标题/表头/单元格及链接段落关联，
  扩充按共同结构定义的确定性规则；不按数据集名、qid、题面或 gold 在产品中分支。
- 逐字引句及来源范围必须可核对；碎片、未知关系及不完整范围回原混合检索。
  名单/计数只返回独立证据，不在 Search 中计算答案（PRD §2.1、D33）。
- 随改动补计划适用、事实/原文投影、未覆盖来源、未解释声明、冲突、超限等诊断。
  诊断直接随本轮 pipeline 落盘，不另设官方对照阶段。
- 先跑 CorporateBench、TempReason、HybridQA、FEVEROUS。仅在诊断证明上限是实际原因时，
  才做 `evidence_limit` 的单变量对照；保持完整性判据与双预算。
  官方 JSON 三元组及 UPDATE 包装留到能单独验证该输入时再做。

### P2：多证据选择、顺序与覆盖

主验证用 MuSiQue、LongMemEval、LoCoMo、MedMemoryBench、HybridQA、FEVEROUS；
CorporateBench、MQuAKE、TempReason 用作已有优势的回归。

1. 从现有失败结果核对源文本、候选、返回与模型输入，判断必要证据丢在何处。
   不仅凭错答或裁判判词认定检索失败。
2. 固定候选池先比较一次 rerank 开/关，再单独比较去重、来源覆盖或片段组织。
   候选规模、Add 输入、答案预算、模型和评分器保持一致；不把多个改动一起归因。
3. 保留多跳连接点与各段支持来源，让长历史覆盖不同事件阶段，避免相似复述占满位置。
   日期、说话人、表头及文档身份跟随来源，各独立片段自定界，跨 Add 不伪造连续对话。
4. 最终仍按既定双预算按段输出；改变已锁定顺序/选择语义时同步设计决定。
   Add 不生成 LLM 摘要，Search 不生成答案（PRD §7.2、§2.1）。

MuSiQue 同时报可答准确率与不可答拒答结果，FEVEROUS 同时报标签、严格证据组和证据指标；
HybridQA 同时报 EM/F1。指标拆分用于判读原有评分，不冒充 AML 维度成绩。

少量正确来源 oracle 可用于诊断，答案 prompt 与裁判固定，gold 只在诊断选源中出现。
正确来源仍无法作答的案例要单列模型上限，避免无依据扩大上下文或继续重复检索。
F1 的本轮代理验证仅限已有长历史问题，不把 LongMemEval 总分当作全局摘要专项分。

### P3：偏好、个人背景与误用控制

本轮缩为现有 QA 能覆盖的 E1/E3 及证据误用控制：

- 保留个人声明者、偏好的否定/例外、有效状态与相关背景，区分用户声明、助手建议和被引用内容。
- 用 HaluMem、MedMemoryBench、LongMemEval 验证；HaluMem 同时报 Correct/Hallucination/Omission。
  LoCoMo 和 MemTrap 作为来源/冲突/负迁移回归，不把 `role` 一律当作真人身份。
- 若需要更强个性化专项，可使用已有 PersonaMem-v2 pipeline；
  先补 `_build_personamem_items` 的答案 token 前缀截断，再建立修复后同口径基线。
  这是已有第十二份入口的补充验证，旧完整历史分不可复用，也不混入当前十一份历史主表。
- H2 条件披露、G3/G4 工作流/模拟、I1/I2 在线反馈完整专项暂缓。
  CL-Bench/BEAM 的旧基础设施阻断未解决时不加入必跑队列；ScriptMem/Doc-PP 采集重放也不进入本轮。

没有相应端到端指标的能力只能报告“本轮未覆盖”。用户隔离、Add 幂等、原文来源和显式冲突等
已有正确性约束仍按代码改动范围回归，不因暂缓某项评分而放宽。

## 五、跑批顺序与采纳条件

1. **现有失败题开发验证。** 从已保存 native 结果中固定失败案例和正确对照，保留题号及完整原始语料；
   每次产品改动按新增行为补必要测试，再通过 HTTP runner 做少量端到端冒烟。
   这属于 P1–P3 各阶段的验证，不增加官方对照前置工作。
2. **按阶段跑关联数据集。** 使用各自 `--frozen` 配方；原十一份选题仍为 3,001 题，
   不为了方便把所有数据集 `--limit` 设成同一个数。失败题开发结果不冒充完整子集结果。
3. **留出验证及最终回归。** 开发案例之外保留未用于调参的问题/场景；候选方案过留出验证后，
   最终串行重跑全部十一份冻结子集，比较当前完整历史参照并保留逐题赢/输。
   接近噪声的小幅变化需要复核，不能只挑已知失败题报涨幅。
4. **冻结实际输入与模型。** 代码、配置、数据、题号、Add 形态、模型及 prompt 留指纹，
   每阶段使用新 run-id。变更影响持久化派生数据时独立建库/重建，不沿用旧索引或旧答案缓存。
   纯排序对照可复用已核对一致的原文库与候选，语料与 scorer 不变。
5. **串行跑，错误不删题。** 网关现有限制下只跑一条回答/判分链。保留回答/裁判错误，
   技术故障修订单独登记，不靠删除失败题或改判分制造产品收益。
6. **采纳端到端改善。** 在关联数据集与留出验证上有可复现收益，最终回归无明确系统性退化；
   原文引句、有效状态、范围完整性、用户隔离、幂等及 `top_k=100` 等不变式通过。
   本轮只报原指标及覆盖范围，不估算九维平台分或新版 Full 总分。

推荐的实际次序是：**P1a 状态更新 → P1b native 取证覆盖 → P2 多证据组织 → P3 偏好与误用控制**。
每阶段先跑关联数据集，最后汇总十一份；官方输入对照与目标提交模型复核保留为之后的独立任务。
