# HybridQA（dev）数据集统计报告

**数据源**：`dataset/hybridqa/`——`dev.json`（题目）、`dev_reference.json`（金标 + 官方评测分组）、`wiki_tables_with_links.tar.gz`（语料：每表的整表 + 全部超链接段落）。
**加载口径**：[`eval/datasets/hybridqa.py`](../eval/datasets/hybridqa.py)——**一个 `Sample` = 一张表**（`table_id` 哈希成 `user_id`），语料是该表的**全部行 + 全部关联段落**，**一题不漏地挂在同一张表下**。
**Tokenizer**：`o200k_base`（tiktoken，§6.4）。⚠ 本数据集**不提供**任何 token 字段，全部为本次重算。

> ⚠ **本地语料目前是不完整的**：`dataset/hybridqa/request_tok/` 只解出 **620/3,053** 张表，`tables_tok/` **完全没解**，`corpus-manifest.json` 也不存在 ⇒ **加载器当前会直接报错**（`read_corpus` 要两个目录 + receipt 三方校验），必须先 `make fetch-data hybridqa`。
> **本报告的数字不是从这 620 个文件算的**——我按加载器的 `_corpus()` 逻辑，从 tar 包中**按 dev 表 id 精确抽取全部 6,106 个语料文件**后重算（⚠ 31 个表 id 含 `:`，Windows 上无法直接打开，经改名副本读取）。**语料范围 = 加载器实际会投喂的全部内容**。

| 成分 | 消息数 | Token 合计 | 占比 | 单条均值 |
| --- | ---: | ---: | ---: | ---: |

⚠ **与前三份数据集的关键差异**：HaluMem / MedMemory / MemTrapBench 的对话都是**助手长回复主导**（assistant 占 ~77%），HybridQA **完全没有助手**——token 的 **79.8% 在链接段落**，主体的 17.7% 在表格行，表头只占 2.5%。

## 三、记忆问题类型及数量、占比统计表

**官方标签**：HybridQA **没有**问题类型（question type）标签。它提供的是**官方评测分组**——`dev_reference.json` 的 `table` / `passage` 两个 id 列表，上游 `evaluate_script.py` 用它把分数拆成 **"table exact/f1"** 与 **"passage exact/f1"** 两组报出。下表**原样采用官方分组**，未自行替换。

| 官方分组（`dev_reference.json`） | 数量 | 占比 | 官方用途 | 说明 |
| --- | ---: | ---: | --- | --- |
| `passage` | **2,025** | 58.4% | 官方报 `passage exact` / `passage f1` | 两个列表**互斥**（交集 0），合计 3,374 |
| `table` | **1,349** | 38.9% | 官方报 `table exact` / `table f1` | — |
| （两列表之外） | **92** | 2.7% | 只进 `total exact` / `total f1` | 上游**未给出**第三类名称，加载器里叫 `other` |
| **合计** | **3,466** | 100% | `total exact` / `total f1`（分母 = 3,466） | — |

> ⚠ **不得冒充**：官方**没有**给这三个分组任何语义解释（发布文件里只有裸 id 列表）。把它们读成"答案在表里 / 答案在段落里 / 需要两者"是**推断**，不是官方定义——**本文档不作此断言**。

**次要的官方字段**：`dev.json` 带 `question_postag`（问句的词性标注串，均值 18.7 个 tag）——是构造期的中间产物，**不是分类标签**。

## 四、不同记忆能力的特点与代表性问题

⚠ **本节为推断**（依据题面 + 官方分组 + 语料构造），**非官方标签**。**多标签口径**：一题可归多条能力，比例之和 > 100%；官方分组见上表。

| 记忆能力（推断） | 题数（估） | 语料规模（均值） | 代表性问题（逐字取自数据） |
| --- | ---: | --- | --- |
| **表格结构化检索** | ~1,349（`table` 组） | 15.9 行 / 8,558 token | *"How many years was the Mexican billionaire Slim ranked as the richest person in the world by the Forbes business magazine ?"* → `3` |
| **跨段落 + 表格的实体消解** | ~2,025（`passage` 组） | 33.3 段 / 8,558 token | *"What is the middle name of the player with the second most National Football League career rushing yards ?"* → `Jerry`（先从表定"第二多"是谁，再进其段落取中名） |
| **多跳关联推理**（数据集核心定位） | 全部 3,466 | 50.2 条消息 | *"What is the difference in time between José Reliegos of Spain and the person born 5 September 1892 who competed at the 1928 Olympics ?"* → `0:06`（两次定位 + 一次数值比较） |
| **超链接图上的证据追踪** | 全部 3,466 | 33.3 段/表 | 段落靠 `Link: /wiki/...` 与单元格里的 `(links: ...)` 勾连；**加载器不告诉模型哪一段相关** |
| **聚合与比较（superlative / 差值）** | 大量 | — | *"How many successors were born in the month of August ?"* → `2`；*"What is the area of the national park whose terrain is extremely rugged…"* → `524 km` |
| **拒绝噪声**（横切） | 全部 3,466 | — | 每题的上下文里**含大量无关段落**（均值 33 段，最多 209 段），实际相关往往只有 1–2 段 |

**各官方分组的难度特征（量化）**

| 官方分组 | 题数 | 关联表数 | 语料 token 均值 / 中位 | 行数均值 | 段落数均值 |
| --- | ---: | ---: | --- | ---: | ---: |
| `passage` | 2,025 | 1,797 | 8,579 / 7,550 | 15.9 | 33.5 |
| `table` | 1,349 | 1,234 | 8,704 / 7,588 | 16.0 | 33.7 |
| `other` | 92 | 89 | **6,787** / 5,074 | 14.3 | 27.8 |
| **全体** | **3,466** | **3,053** | 8,558 / 7,496 | 15.9 | 33.3 |

> **可读出的结论**：**官方分组不区分语料规模**——`table` 与 `passage` 两组的 token 均值只差 1.5%、行数完全相同（16.0 vs 15.9）。也就是说**"答案在哪一侧"与"语料有多大"无关**，两个分组拿到的是**同等量级的上下文**。真正的成本变量是**段落数**（2–209，方差极大），不是分组。

## 五、数据集结构及字段说明

**格式**：3 个部分，**题目/金标是 JSON 数组/对象，语料是 per-table 的 JSON 文件树**。

```
dev.json                  JSON 数组，3,466 条
  [ {question_id, question, table_id, answer-text, question_postag}, … ]

dev_reference.json        一个 dict，三个键必须成对校验（加载器强制）
  { "reference": {question_id: 答案串},     ← 3,466 条，单独的真源
    "table":     [question_id, …],          ← 1,349，官方评测分组
    "passage":   [question_id, …] }         ← 2,025，与 table 互斥

tables_tok/{table_id}.json    整表（结构化，未文本化）
  { "title": str, "header": [[text, [links]], …], "data": [[[text,[links]], …], …],
    "intro"?, "section_title"?, "section_text"? }

request_tok/{table_id}.json   该表的全部超链接段落
  { "/wiki/Page_Name": "段落正文", … }      ← 3,053 个文件，共 101,753 段

corpus-manifest.json          语料收据（sha256 + archive_sha256）——⚠ 本地缺失
```

**组织关系与关联**

- **表 → 问题是一对多（3,053 : 3,466，最多 1:4）**；**问题 → 表是严格一对一**。加载器**按 `table_id` 分组**：同一张表的题共享同一段 `Add` 语料 ⇒ 语料只投喂一次（这解释了为什么"500 题"这类说法在 HybridQA 上等于"305 张表"）。
- **`table_id` → `user_id`**：`"hybridqa-" + sha256(table_id)[:20]`——**表即用户**，题**不**进 `user_id`。这与 LoCoMo/LME 的"题即用户"完全不同。
- **时间戳**：⚠ **完全没有**。题目、金标、表格、段落**都没有任何时间字段**（加载器也不合成）。
- **标准答案**：`dev_reference.json` 的 `reference[qid]` 是**单个字符串**，与 `dev.json` 的 `answer-text` **必须逐字一致**（加载器对此硬校验，不一致即 `ValueError`）。**答案是极短的抽取式span**——均值 **12.3 字符 / 2.1 词**（最长 109 字符）。
- **证据定位**：⚠ **没有 `evidence` 字段**。定位信息**隐含在超链接里**——单元格 `(links: /wiki/X)` 与段落键 `/wiki/X` 对应，但**加载器刻意不读 answer-node、不挑答案行/段落、不注入题目或答案**（见模块 docstring）。**因此无法做证据级 oracle 诊断**。
- **判分口径**：**上游固定版本的 `evaluate_script.py`**（在 `dataset/.upstream/hybridqa/`）：`normalize_answer` 做小写 + 去冠词 + 去标点 + 折空白，再算 **EM** 与 **token-F1**；分组报 `table/passage` 两组，外加 `total`。

**重复与去重**

| 层面 | 是否重复 | 去重方式 |
| --- | --- | --- |
| `question` 文本 | **无**（3,466 唯一） | 不需要 |
| 答案串 | 少量（2,976 唯一 / 3,466，重 490） | 短答案天然重名（`3`、`2`、`Yes`），**不是数据问题** |
| `table_id` → 用户 | **无重复**；一表多题是**分组共享**，不是重复投喂 | 按 `table_id` 分组即可 |
| 段落正文 | **有**（101,753 段 → 73,071 唯一），**28,682 段跨表重复** | 按正文去重 → token 26,127,222 → **18,841,804** |
| `tables_tok` / `request_tok` 文件名 | 31 个含 `:`（Windows 非法） | 加载器 `safe_table_id()` 只挡 `/\` 与 `..`，**不挡 `:`** ⇒ **依赖 `make fetch-data` 的发布层处理**，见下 |

## 六、简短总结

- **规模**：**3,466** 题 / **3,053** 张表（= 用户） / **153,290** 条语料消息 / **2,613 万 token**；单表均值 **8,558 token**（中位 7,496，1,150–47,720）。**零前缀展开**——题与表一一绑定，原始规模 = 投喂规模。
- **主要考察的记忆能力**：**异构多跳**——在"结构化表格 + 非结构化百科段落"两种形态之间做实体消解、聚合与比较。官方把题分成 `passage`（58.4%）/ `table`（38.9%）/ 未分类（2.7%）三组，仅用于**分数拆分**，**没有**任何语义或难度标注。
- **最突出的评测特点**：
  1. **上下文全是噪声**——一题拿到整张表 + 全部 33 个（最多 209 个）链接段落，**加载器不挑证据、不给提示**，考的是"从 50 条消息里自己找出那 1–2 段"；
  2. **表即用户**——`user_id = sha256(table_id)`，一表多题共享同一份 `Add` 语料（3,053 用户 : 3,466 题），**不是 3,466 个用户**；
  3. **抽取式短答案 + 官方 EM/F1**——答案均值仅 2.1 词，判分复刻上游固定版本函数，**口径稳定**，是本仓少见的"非 LLM 裁判"评测；
  4. **无时间戳、无证据字段、无 assistant 消息**——无法做时间推理、无法做证据 oracle、语料全部渲染成 `role: user`；
  5. **⚠ 本地语料尚未就绪**——`tables_tok/` 未解、`request_tok/` 只有 620/3,053、`corpus-manifest.json` 缺失，**当前跑不了**，须先 `make fetch-data hybridqa`；本报告的数字是从 tar 包按需抽取全部 6,106 个语料文件后重算的。
