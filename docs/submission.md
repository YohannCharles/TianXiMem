# 提交台账

> 最后核对：2026-09-23，对应 PRD §2.4 / §12.1 / §12.5 / §16 / §17.1。**冲突以 PRD 为准。**

## 为什么这份文档必须存在

**AML 的机会成本是硬的**（§2.4）：

| 层 | 限制 |
| --- | --- |
| **Smoke** | 每轨道 **≤30 次**，每小时 1 次，**不进榜** |
| **Full** | 每 Key 每轨道 **2 次**，第二次需等第一次完成 **30 天后**；**一旦接受即版本冻结，不能因成绩不佳撤换** |

**"版本冻结"意味着"这次 Full 提交的是哪个 commit + 哪份配置"是必须留痕的信息**——赛后能否复现、能否解释分数，全依赖这一条记录。**没有任何自动机制会替你记住它。**

## 3. S 未知的清除记录（§17.1）

**S1 是整张悬而未决清单里唯一"信息不足且后果最重"的一条**（§17.1）。**Smoke 第一次跑通后，第一件事就是设计一个能判别它的最小实验。**

| # | 未知 | 状态 | 是哪次 Smoke 清掉的 | 结论 |
| --- | --- | --- | --- | --- |
| **S1** | AML 取哪个字段（`content`？`text`？），是字符串还是整个 dict | ⬜ | | |
| **S2** | 线上是否真按 20 条 / 2,000 词切批，"Adapter 计的词"怎么算 | ⬜ | | |
| **S3** | `created_at` 是否被 CL-Bench 那条路径消费 | ⬜ | | |

### S1 的结论会决定一件大事

| S1 的答案 | 后果 |
| --- | --- |
| 取 `content`、是字符串 | ✅ 原设计成立 |
| 取 `text` | ⚠️ CL-Bench 路径会**整批丢弃**我们的记忆 → 需同时带 `text` 字段 |
| 按 **dict** 处理 | ⚠️ 模型读到**原始 JSON** → §11.3 的整个打包策略要重做 |

**两个失败模式都不报错**——所以"跑通了、分数还行"**不构成** S1 已清除的证据。

**兜底方案**（**不要提前上**）：返回项里同时带 `content` 与 `text`。**这属于契约外的赌注，要等 Smoke 的实测结果再决定。**
