# 悬而未决清单

> 最后核对：2026-09-23，对应 PRD §17（+ §6.4 要求补入的一条）。**冲突以 PRD 为准。**

## 为什么要单列一张表

前面各节的"待验证"散落在各处，集中成一张表后，每一类都标了它**由谁消除**、以及**不消除会在哪一步变成阻塞**。

> **最贵的错误是拖到 Step 5 才发现某个未知没清**（§17 引言）。

本表要**当作 checklist 用**——每个 Step 开始前扫一遍，看有没有条目正好卡在这一步。

> ### ⚠ S1 是整张表里唯一"信息不足且后果最重"的一条
>
> 其余各项要么能用实验回答，要么已经对冲。**所以 Smoke 第一次跑通后，第一件事就是设计一个能判别 S1 的最小实验。**

> **判别实验**：Smoke 不返回答案文本，只能用端到端信号——**加一条只有它能回答的记忆，看分数是否变化**。
>
> **两个不报错的失败模式**（详见 `docs/contract.md` §5）：AML 按 dict 处理返回项 → 模型读到原始 JSON；CL-Bench 那条路径读 `text` 字段且**缺 `text` 的项会被直接跳过** → 整批退化成 `(no memories)`。
>
> **兜底但不要提前上**：返回项里同时带 `content` 与 `text`。这属于**契约外的赌注**，要等 Smoke 实测结果再决定。

## 17.3 规则解释风险（不可控，只能对冲）

| # | 风险 | 对冲 | 状态 |
| --- | ---- | ---- | ---- |
| **P1** | `/rules` 有"不限定模型"的字面表述，与 §2.3 的模型规定冲突；issue #19 零回复 | **按模型规定执行**——两种读法下都合规 | ✅ 已决（执行中） |
| **P2** | 数据禁止训练（AML 条款 + CLBench 许可证双重封死） | **不微调，无对冲余地** | ✅ 已决 |
| **P3** | 代理评测 → 全赛道不可线性外推 | 只在代理上做**相对**比较，**不做绝对外推** | ✅ 已决（执行纪律） |

> 这里用 `P` 编号，是为了**不与 §12.1 的"风险 R1"撞名**——那个 R1 说的是模型替换，两回事。

**P1 的细节**：`/rules` 另写着"不限定你使用的数据库、索引、向量模型或内部架构"，与模型规定表字面冲突；AML 的 issue #19 触及此事（**主体是超时/重试策略，模型规定只是第三问**）且零回复。**本项目不据此放松**——按模型规定执行在两种读法下都合规。

**P2 的细节**：AML 数据条款明文"Use this data only for the evaluation. Do not train on it"，CLBench 许可证同样禁止训练/微调/蒸馏。**这是双重封死，"微调模型"不是暂不实现，是不允许。**
> ⚠ **但这两条在归档里都没有出处**（全库检索 `only for the evaluation` 等措辞零命中），属**单边来源**，引用前须回原始页面/许可证文件复核。**结论不变，但不要把它当成已归档的实证。**

## 维护约定

- 清掉一条时**不要删行**——把状态改成 ✅ 并在"结论"里写清**怎么清掉的**（哪个实验、什么数字、哪次 Smoke）。结论比状态有用。
- 新发现一条未知时，**先判断它属于哪一类**：本地能验证 → 加进 `docs/experiments.md`；只能靠 Smoke → 加进本表 17.1；只是规则解释风险 → 17.3。
- **阻塞级别要写具体 Step 号**，不要写"尽早"——那是没法排期的。
