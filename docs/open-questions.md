### S5 的现状

两个短语整页都不存在，单条超长的处理**整份文档没有任何规定**，官方口径是**去问主办方**。
⇒ **"会切开"与"不会切开"两个方向都没有依据**，只能观测——而**观测点只有一个**：
AML 调我们 `/add` 的那一刻。

**怎么观测（按成本排序）**：

1. **问主办方**——官方文字明确让你问。一次把 S2 的另一半（"词怎么数"）也问掉，同一个渠道。
2. **在 Add 入口数一个量**：**本批内相邻同 role 的消息对数**。看到就是看到了，不需要推断。
3. **零代码的替代**：Smoke 跑完后对 SQLite 跑一条只读 SQL——
   `SELECT count(*) FROM qa_pairs WHERE question IS NOT NULL AND answer IS NULL;`
   ⚠ **基线不是 0**：LoCoMo 有 144/272 个 session、LongMemEval 有 8/23,867 个 session
   **以 user 消息结尾**，它们天然产生"有问无答"的对。判据是**同一个 session 内连续出现多个**。

**本地复现不了**：harness 的切批是我们自己做的，**永远看不到 AML 的实际行为**——
别指望代理评测回答这一条；它能回答的只是"若碎片存在，值多少钱"。

**若答案是"会切开"**：**不需要再改代码**——[D20](./decisions.md) 已经让配对在两种答案下都成立。

### S6 的现状

**官方对此没有规定——而且这次是"连问都没得问"**：我们查过 [`contract.md`](./contract.md) 与 PRD §2.1/§2.2，**没有任何一句承诺 Add 的顺序**；PRD §6.1 自己还写着"**`event_time` 保证不了 session 内顺序**"。⇒ **顺序是我们这边的隐含假设**（[D20](./decisions.md) 的配对判据整条建立在它上面）。

**三条旁证说风险不为零**（旁证，不是证据）：

1. **两个参考实现都专门写了顺序重建**——ReFind 用正则从 `request_id` 里解析 chunk 序号（`eval/baselines/refind/app/store.py:50-58`），候选映射仓库按源时间戳重排。**那两队跑过真平台。**
2. ReFind 的申报表写着**建议 Add 并发 16** ⇒ 平台会并行投喂。
3. `(user_id, session_id)` 串行锁只保证"一次一个"——**它排的是到达顺序**；并发下到达顺序 ≠ 发出顺序。

**本地复现不了**：harness 是自己顺序发的，send order 必然等于 arrival order。**别指望代理评测回答这一条**（同 S5）。

**要清它得先"看得见"**——**其中有一条零代码的路**（与 S5 的"零代码替代"同形）：

1. **✅ 跑完真 run 后对 SQLite 跑一条只读 SQL**（**不需要改代码**，2026-09-25 补）：
   `qa_pairs` 里 **`pair_idx` 是到达顺序**、**`event_time` 是该对首条消息的时间戳**，两者一比就知道有没有晚到：

   ```sql
   SELECT user_id, session_id, pair_idx, event_time,
          LAG(event_time) OVER (PARTITION BY user_id, session_id ORDER BY pair_idx) AS prev
   FROM qa_pairs
   WHERE event_time IS NOT NULL;
   -- event_time < prev 的行 = 疑似晚到批次（到达顺序与源时间顺序不一致）
   ```

   ⚠ **两种"正常"也会让它非 0**：①该 session 的 `event_time` 缺失（`IS NOT NULL` 已滤掉一部分，但**整段都缺**时这条 SQL 看不见这个 session）；②**对话本身在时间上回跳**（回忆、倒叙）。⇒ 判据是"**同一个 session 内连续多处**"，不是"出现一处"。
2. **在 Add 入口记一行** `request_id` + 到达时间（要改代码，**本次没做**）——比第 1 条多一个信息：能看出**差了几批**；
3. **问主办方**（与 S5 同渠道，一次把两条问掉）。

> **为什么没顺手加个探测器**（2026-09-25 的决定）：加它要动 `pairing/` 或 `service/pipeline.py`，还要给 `store/` 加一张表。在**风险尚未验证**的前提下，**先保住既有数字的可比性更重要**——ledger 里的 A3 / `mem-date` / `cov-wide` / `n1-best` 全都建立在**同一套配对**之上。
>
> 代码里那个"本可以发现乱序、却没发现"的缺口**不是遗漏，是刻意留的**——上面那条就是原因。

**若答案是"会乱序"**：修法只有一条——**把配对从 Add 时搬到读时**（= ReFind 那套：只存原文，Search 时按源时间戳 + `request_id` 序号重建）。代价是 **§6 整层重写**，且 ledger 里所有既有数字**失去可比性** ⇒ **那是个决定，不是个实现**（先估，再动手）。

### S7 的现状

**来源是参考实现的观测，不是我们的推断**：ReFind 的改编说明第 3 条写着
"The platform **may assign one `session_id` to all chunks for a sample**"（逐字，见
[`../eval/baselines/refind/docs/METHOD_CARD.md`](../eval/baselines/refind/docs/METHOD_CARD.md)）。
它的理由是**反过来的**：他们原本按"见过就排除整个 session"去重，发现那样会把**整个样本**排除掉。

**对我们的影响面**：`session_id` 是我们三个机制的作用域——**配对**（连续 user 判定、跨批续接）、
**扩窗**（同 session 才扩，`rank/neighbor.py`）、**段合并分组键**（`(user_id, session_id)`）。
粒度变粗后三者照旧运行，**不报错**，但"session"不再等于"一段对话"。

> **不致命**：三处只要求"同一个 session 内 `pair_idx` 有序"，这个不变量**不会**因粒度变粗而破。
> 所以这条更像"语义漂移"而非"功能失效"——**但它是 Full 之后才可能被察觉的那一类误会**。

**本地复现不了**：我们本地喂的 `session_id` 是加载器自己定的（[`../eval/datasets/`](../eval/datasets/)），
**平台给什么我们只能从真 run 看**。⇒ 与 S6 **一起清**——观测点是同一个（Add 入口），**但那个观测点现在还不存在**（见 S6）。
