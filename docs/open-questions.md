### S5 的现状

**官方对此没有规定**：一手来源（官方 api-guide）里 `sentence boundary` / `complete message`
两个短语整页都不存在，单条超长的处理**整份文档没有任何规定**，官方口径是**去问主办方**。
⇒ **"会切开"与"不会切开"两个方向都没有依据**，只能观测——而**观测点只有一个**：
AML 调我们 `/add` 的那一刻。

**怎么观测（按成本排序）**：

1. **问主办方**——官方文字明确让你问。一次把 S2 的另一半（"词怎么数"）也问掉，同一个渠道。
2. **在 Add 入口数一个量**：**本批内相邻同 role 的消息对数**。看到就是看到了，不需要推断。
3. **零代码的替代**：Smoke 跑完后对 SQLite 跑一条只读 SQL——
   `SELECT count(*) FROM qa_pairs WHERE question IS NOT NULL AND answer IS NULL;`
   ⚠ **基线不是 0**：LoCoMo 有 144/272 个 session、LongMemEval 有 8/23,867 个 session
   **以 user 消息结尾**，它们天然产生"有问无答"的对。判据是**同一个 session 内连续出现多个**。

**本地复现不了**：harness 的切批是我们自己做的，**永远看不到 AML 的实际行为**——
别指望代理评测回答这一条；它能回答的只是"若碎片存在，值多少钱"。

**若答案是"会切开"**：**不需要再改代码**——[D20](./decisions.md) 已经让配对在两种答案下都成立。

### S2 的现状（**仍是"一半"**）

**已答**：切批的**边界规则**——「每个来源会话默认调用一次 Add，超过 20 条消息或 2,000 个
Adapter 计数的词时确定性分段」。出处：[`contract.md`](./contract.md) §7.1（**一手来源**：官方 api-guide）。
⚠ **"消息会不会被从中间切开"不在已答之列**——那是 **S5**。

**仍未答**：**"词"怎么数**——官方只写"按冻结 Adapter 计数"，**没有给计数定义**。
⇒ `pending_*` 与线上对不上这条**仍然成立**，那三个计数器仍然只能用来验证续接逻辑自洽。

**⚠ 这一半的缺口只落在 `answer` 侧**："本批要续写哪一对"的判据是
`status = 'pending' OR answer IS NULL`（[D20](./decisions.md)）⇒ **question 侧不依赖词数计数**。但"**这一对的答话还没写完**"没有任何内容依据可判
（一个已有 `answer` 的对和写完的对长得一模一样）⇒ **answer 侧仍然受 S2 影响**。
⇒ 想彻底摆脱它，只能问出计数口径。

**已量的影响面**（全量两份数据，词数用空白切分近似）：LoCoMo 最长单条 **87 词**、从不触到词数上限
⇒ **两条路径在它上面完全重合**；LongMemEval **40% 的 session 首批被词数上限切开**（9,528/23,867）。
**别用 LoCoMo 的"完全重合"外推 LongMemEval**（`docs/roadmap.md` 的数据侧也记了这一条）。

> ### ⚠ S1 是整张表里唯一"信息不足且后果最重"的一条
>
> 其余各项要么能用实验回答，要么已经对冲。**所以 Smoke 第一次跑通后，第一件事就是设计一个能判别 S1 的最小实验。**
>
> **判别实验**：Smoke 不返回答案文本，只能用端到端信号——**加一条只有它能回答的记忆，看分数是否变化**。
>
> **两个不报错的失败模式**（详见 `docs/contract.md` §5）：AML 按 dict 处理返回项 → 模型读到原始 JSON；CL-Bench 那条路径读 `text` 字段且**缺 `text` 的项会被直接跳过** → 整批退化成 `(no memories)`。
>
> **兜底但不要提前上**：返回项里同时带 `content` 与 `text`。这属于**契约外的赌注**，要等 Smoke 实测结果再决定。

### V7 的结论（**2026-09-24 全清**）

网关**默认不开思考**——实测探针（只让它回 `OK`）：

| 网关默认 | `content` | completion_tokens |
| --- | --- | --- |
| **改之前** | `'Thinking Process:\n\n1. **Analyze the Request:**...'`（推理混在 `content` 里，**不是**单独的 `reasoning_content` 字段） | **167** |

**为什么这条曾经是硬阻塞**：归档的 7 个 pipeline 里**只有 `pipeline_beam.py` 传 `enable_thinking: False`**，而代理评测真正用的 **LoCoMo-Refined 与 LongMemEval 都没传**。网关默认开着 ⇒ 推理过程会进 `generated_answer` ⇒ **裁判读到的是推理而不是答案**，且不报错。

**⇒ 归档 pipeline 可以直连网关，不需要自己加一层 shim。** 探针已固化进 `make check`（LLM 那一项）——**每次环境自检都会重新验一遍**，所以它回退成"默认开"不会静默。
