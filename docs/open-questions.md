### S5 的现状（**已清**，2026-10-01）

**答：会切开。** 观测点就是当初指定的那一个——**AML 调我们 `/add` 的那一刻**
（请求原文采集，官方 43,272 条 add / 454,937 条消息全量）：

| 问题 | 实测 |
| --- | --- |
| 整条放行还是切开？ | **切开**。**单条消息硬上限 ≈8,000 字符**：2,514 条正文正好 8,000 字符，**0 条超过** |
| 切在哪？ | **不在句边界，是硬切**。实测切点落在半个 token 上：`…"row_span": "` → 下一条以 `Corpus: 1"…` 开头；`…lost to [[Se` → `Corpus: rena_Williams|Serena]]…` |
| 切成什么形状？ | **连续的多条同 role 消息**，每片**重新带 `<标签>: ` 前缀**，且**拼回去是全文**（不是截断）。逐字验过某条 35,523 字符的源正文切成 7 片（位置 0 / 7,930 / 11,039 / 18,969 / 21,368 / 29,298 / 32,389，覆盖 35,522/35,523） |
| 片落在哪？ | **落进不同的 Add**（每条 add ≤20 条消息），所以单条 Add 的合并块通常很小<br>⚠ 例外：采集里有 **79 条** add 的合并块在 30k–160k 字符之间——那是平台自己的 `Streaming …` 判分回写，**不是记忆语料** |

⇒ **结论不变（会切开，切点不在句边界），但兜底的规则换过一轮，所以"S5 已经收口"要重读**：
D20 当年把连续 user 并进同一个 `question` 来兜这件事，**D32（2026-10-03）把这个取舍反过来了**
⇒ **`q q q a` 现在的产出是 `[q] [q] [q+a]`，前面那些 `q` 有问无答**。
换来的是一份被切碎的长文档不再合成 **38,270 token** 的块（线上静默截断、本地网关 400）。
⇒ **"有问无答"的片段是 D32 明写接受的状态，不是缺陷**；规则仍然按 role 拼、不依赖切点。

⚠ **剩下的是"本地复现不了"**：`batching.py` 只复现"20 条"那一路，**不发**切分
⇒ CL-Bench 那种 158,789 字符的单条正文本地会整条发出去（服务端大概率 500）。
**线上不会**。这条与嵌入网关的上限叠在一起，见 **V15**。

> ⚠ **顺带记一条边界**：`docs/` 里"Add 时按 message 切块"说的是 **InvMem 候选**
> （[`reference-implementations.md`](./reference-implementations.md) 那张表的第三列，
> [`chunk_document`](../eval/baselines/invmem-candidate/src/vanilla_rag/chunking.py)
> 的 320 token 块）——**不是我们**。我们的形态是 **Add 时配对、块级**。

### S2 的现状（**仍是"一半"**）

**已答**：① 切批的**边界规则**——「每个来源会话默认调用一次 Add，**达到 20 条消息或
2,000 个 Adapter 计数的词中的任一边界时确定性分段**」；② **词数的计数口径**——
一手来源原话是 `2,000 **Adapter-counted** words`：**由那个冻结的 Adapter 计**，
而它冻结 ⇒ 是确定的。出处：[`contract.md`](./contract.md) §7.1（**一手来源**：官方 api-guide）。

⚠ **"消息会不会被从中间切开"是另一个问题，且已有答案**——那是 **S5**，
2026-10-01 实测：**会**，单条硬上限 ≈8,000 字符（见上面 S5 那一节）。

**仍未答（注意口径）**：**不是"官方没定义"**，而是**本仓复现不了那个计数**——
那个 Adapter 是**平台侧的冻结组件**，我们没有它 ⇒ 不知道它把什么算作一个词。
⇒ 本地按"20 条 + 自造的规模近似"切批，**批界与线上不保证一致**。

> ⚠ **新冒出来的一处对不上**（2026-10-01 实测）：官方口径是 2,000 个**词**，
> 而实测的片长看起来是**按字符**卡的——**2,514 条正好 8,000 字符、0 条超过**，
> 且**英文散文与数字表格落同一个数**（若按词/token 计，数字表格的字符数应明显更少）。
> **两者的换算没对上**，两种可能：那个 Adapter 就是按字符计；或者边上还叠着一层字符硬上限。
> 单查这一条不需要平台配合——**把 8,000 字符附近的样本按内容类型分开再量一遍**即可。

**2026-09-27（[D24](./decisions.md)）把它的后果收窄成一条**：**本地复现的批界与线上不一致
⇒ 被批界切成两半的 QA 对数对不上**（实测 LoCoMo 全量 63/3,075）。
**本地分数与线上的差距里，这一条要算进去。**

⇒ 想彻底摆脱它，要么拿到那个 Adapter 的计数口径，要么**问主办方**它按什么数。

**已量的影响面**（全量两份数据，词数用空白切分近似）：LoCoMo 最长单条 **87 词**、从不触到词数上限
⇒ **两条路径在它上面完全重合**；LongMemEval **40% 的 session 首批被词数上限切开**（9,528/23,867）。
**别用 LoCoMo 的"完全重合"外推 LongMemEval**（`docs/roadmap.md` 的数据侧也记了这一条）。

### S6 的现状 —— ✅ **已收口（2026-09-29）**

**答案：不带。** 采集层（`capture.enabled`）抓到的**真实外部请求**里，官方发的是

```text
"request_id": "r_31156f4174b24abe83ad2c09a486cc5f398ddc819b4ca9e33b9c94bb1e2caab8"
```

——**不透明、没有 `chunk-`、没有序号**；那一条的 `error` 是 `ValueError`（旧解析取不到序号），
服务回 **500**。⇒ 本表登记的那个风险成真了：**Add 全挂**。

**处置**：**D28** —— `request_id` 回到 **opaque string**，位置改成 `(request_id, local_index)`，
邻接改成 **Add 内显式链**（`prev` / `next`），扩窗与段合并都只在这条链上走。
那条解析逻辑与 `ingest.chunk_ordinal_pattern` 一起**删除**（见 [`decisions.md`](./decisions.md) 的 D28）。

> ⚠ **对当前实现，「序号可不可信」已经不是问题**——D28 之后不从 `request_id` 里读任何东西。
> 留着这一节，是因为下面那条「要不要换成 ReFind 那套」仍取决于它的答案。

**为什么认为它就在请求里**：ReFind 用正则从 `request_id` 里解析 chunk 序号
（[`../eval/baselines/refind/app/store.py`](../eval/baselines/refind/app/store.py) 的 `:50-58`）——
**那队跑过真平台** ⇒ 这曾是 D25 的依据（见下：对**我们的**平台不成立）。

**本地复现不了**：harness 是自己顺序发的，send order 必然等于 arrival order（同 S5）。

> ⛔ **别再去解析 `request_id`**——D28 已定它是 opaque string，看官方发的是什么就
> 直接读采集文件里的原文（见下）。

**最直接的一条路：把官方发来的请求原文记下来**（`capture.enabled`，2026-09-29 落地）。
打开它跑一轮，`/add` 与 `/search` 的**原始请求体**就落在
`var/capture/requests.jsonl`（容器里是 `/data/capture/requests.jsonl`，在卷里可 `docker cp`）——
每一行都有**官方原样发来的 `request_id` 字符串**——这是唯一一手证据。
配置项与四条纪律见
[`config-reference.md`](./config-reference.md) §12 与
[`../src/tianximem/service/capture.py`](../src/tianximem/service/capture.py)。

**另一条路**：**问主办方**（与 S5 同渠道，一次把两条问掉）——它仍是唯一能**证明**
序号语义的路，而不再只是"问一句安心"。
**若答案是"序号语义不对"**（对照实现的做法）：修法只有一条——**把配对从 Add 时搬到读时**（= ReFind 那套：只存原文，Search 时按源时间戳 + `request_id` 序号重建）。代价是 **§6 整层重写**，且 ledger 里所有既有数字**失去可比性** ⇒ **那是个决定，不是个实现**（先估，再动手）。

### S7 的现状

**来源是参考实现的观测，不是我们的推断**：ReFind 的改编说明第 3 条写着
"The platform **may assign one `session_id` to all chunks for a sample**"（逐字，见
[`../eval/baselines/refind/docs/METHOD_CARD.md`](../eval/baselines/refind/docs/METHOD_CARD.md)）。
它的理由是**反过来的**：他们原本按"见过就排除整个 session"去重，发现那样会把**整个样本**排除掉。

**对我们的影响面**：`session_id` 是我们三个机制的作用域——**位置的连续范围**（D24 起组合
只看一次 Add，但**位置**仍按 session 有序）、**扩窗**（同 session 才扩，`rank/neighbor.py`）、
**段合并分组键**（`(user_id, session_id)`）。
粒度变粗后三者照旧运行，**不报错**，但"session"不再等于"一段对话"。

> **不致命**：系统只要求"同一次 Add 内位置有序"（**D28** 起 = `local_index`），
> 这个不变量**不会**因粒度变粗而破（D28 之后连"跨 Add 顺序"都不存在了，更谈不上被它破坏）。
> 所以这条更像"语义漂移"而非"功能失效"——**但它是 Full 之后才可能被察觉的那一类误会**。

**本地复现不了**：我们本地喂的 `session_id` 是加载器自己定的（[`../eval/datasets/`](../eval/datasets/)），
**平台给什么我们只能从真 run 看**。⇒ **观测点已经有了**：请求原文采集
（`capture.enabled`）会把官方实发的 `user_id` / `session_id` **原样**记下来——
它已经替 S6 干过一次活（见上面「S6 的现状」），**开一轮跑就能把这条也看清**。

### V7 的结论（**已清**）

网关**默认不开思考**。**实测依据**（只让它回 `OK`）：`content` = `'OK'`、completion_tokens = **2**；

`generated_answer` 里装的是推理过程 ⇒ **裁判读到的是推理而不是答案，且不报错**。

**⇒ 归档 pipeline 可以直连网关，不需要自己加一层 shim。** 探针已固化进 `make check`（LLM 那一项）——**每次环境自检都会重新验一遍**，所以它回退成"默认开"不会静默。
