## §7.1 / §7.2 — 两路

| | 词法 | 语义 |
| --- | --- | --- |
| 实现 | **Qdrant 原生 `qdrant/bm25`**（服务端推理，真 BM25，sparse + `modifier: idf`） | `text-embedding-v4`，经 `embed/` 的 `Embedder` 接口 |
| 查询 | —— | **原样送进去，不做任何改写**；每查询**恰好 1 次**调用 |

**不使用 BGE-M3 的 sparse 输出**：它的 sparse 是**学出来的词法权重而非 BM25**；且提交时的 `text-embedding-v4` **不提供该能力**（§7.1）。

### ⚠ 一条必须实测的假设

**"BM25 反超 BGE-M3 sparse"这条必须带前提说**（§7.1）。在 MLDR 上：

| 分词器 | BM25 | 对比 BGE-M3 sparse |
| --- | --- | --- |
| **Lucene Analyzer** | **64.1** | 反超（62.2） |
| **BGE-M3 自己的 XLM-R** | **53.6** | **明显落败** |

**结论对分词器高度敏感。** 所以"真 BM25"这个选择成立，但理由**不是**"BM25 天然更强"，而是"**配正经分词器的 BM25** 更强"。

> **由此推出一条实现要求**：选 `qdrant/bm25` 时，**它的分词行为要实测一次**（拿一两个多语言长文档的 case 对照），**别默认它等价于 Lucene Analyzer**。

（数据来源：BGE-M3 论文 Table 11。本环境 `arxiv.org` 被拦截，该数值经三个独立二手来源交叉一致。）

## §7.3 — Weighted RRF

```json
{"prefetch": [{"query": <bm25>,  "using": "bm25",  "limit": N},
              {"query": <dense>, "using": "dense", "limit": N}],
 "query": {"rrf": {"weights": [w_bm25, w_dense], "k": 61}},
 "limit": <top_k>}
```

| 要点 | 说明 |
| --- | --- |
| **`k` 必须显式设 `61`** | **不是默认值，也不是文献里的 60** |
| **每个 `prefetch` 都要带 `using`** | 命名向量场景下不写 `using`，Qdrant 无法确定用哪一路 |
| **根级 `limit` 用请求里的 `top_k`** | **不要写死 100**——写死会在 AML 传更小值时变成"返回超限"，那是**契约错误**而不是截断 |
| **每路 `prefetch` 的 `limit`（`N`）必须显式给定** | 初值 **200**，是"进入 RRF 融合的候选池"大小 |
| 权重初值 `[0.5, 0.5]` | **任何调整都必须有 ablation 数据支撑** |

### 两个坑叠在一起（为什么是 61）

- **Qdrant 的默认值是 `k = 2`**（官方文档逐字："k is a constant (set to 2 by default)"）。不设就会得到一个**与所有参考实现都不同的融合行为，且极难排查**。
- **`k = 61` 才等价于 RRF 文献里的 `60`**：Qdrant 的秩是 **0-based**（"the top result has r_d = 0"），公式为 `1/(rank + k)`；文献是 1-based 的 `1/(60 + rank)`，首位即 `1/(0+61) = 1/(1+60)`。

**`k=61` 是正确性常量，不是调参项。**

**版本门槛**：`k` 自 v1.16.0、`weights` 自 v1.17.0 起可用 → 要求 **≥ v1.17.0**，部署时**钉死**。

### 三个不同的量，不要混用

`prefetch_limit`（**200**）· 种子数（**20**，§10）· Top-K（**100**，§2.2）

**融合池上界**：200 × 2 路 = 至多 400 条，要给 100 个名额留出**邻域折叠与去重的余量**。

### 一个简化，以及它的代价

**RRF 只用排名不用分数**，因此 **BM25 分数与余弦相似度无需归一化对齐**——这绕开了 hybrid 检索最麻烦的一步。**代价**：权重代表的是"**名次话语权**"而非"分数重要性"（§7.3）。

## §8 — Evidence Checker

判断当前候选是否已足够回答 Query；足够则直接返回，不足才进入 Agentic Search。

### 判据不能用融合分数

> **RRF 融合后的分数不是校准量。** Qdrant 官方明确警告不要把单路阈值用到根级 `score_threshold`——**"照搬 dense-only 的阈值会静默截断结果"**。

改用**名次一致性判据**：分别跑一次 `bm25-only` 与一次 `dense-only`，用两者返回的**排名**做判断：

```text
足够（Direct Return）：
  两路 top1 相同
  或 两路 top-5 重叠 ≥ 3
  或 bm25 top1 的名次在 dense 结果中位于前 3

否则：
  → Agentic Search
```

**副产品**：这两次分离查询的结果**正是 §13 中 hybrid-vs-BM25-only 对照所需的数据**，**不额外花成本**。

### ⚠ 它依赖 dense 一路存在

**这是一条必然的耦合，不是实现细节**（§8）：

- Checker 的判据建立在"分别跑 `bm25-only` 与 `dense-only`"之上
- 而 §13 的 A2 准备在 "A2 ≤ A1" 时**砍掉 dense**
- **真砍了，Checker 的判据就塌了**

**所以 Checker 是 `dense` 的下游**，退化路径只有两条，**且必须在 Step 1 就选定并写进配置**，不要等到决定砍 dense 的那天再补：

| 退化路径 | 行为 |
| --- | --- |
| `never_agent` | dense 关掉时**一律不触发 Agent** |
| `bm25_gap` | 改用 **BM25 自身的名次间隔**做判据 |

**若 dense 被砍，§13 的 A2 对照同时失去意义**，A1（裸 BM25 单轮）成为唯一基线。

## 边界：本目录到 Rerank 为止

下游是 [`../rank/`](../rank/) 的三连环——**排序 → 扩窗 → 打包**（§10 + §11.2 + §11.3）。本目录**不**做扩窗、**不**做打包、**不**排序。

**唯一需要交接的信息**：Checker 的那两次分离查询（`bm25-only` / `dense-only`）的**原始排名**要留出来——§13 的 A2 对照复用它，**不额外花成本**（§8）。别在 `checker.py` 里把它们用完就丢。

**`top_k` 的最终计数不在本目录**：本目录返回的是候选，**精确 ≤ `top_k` 的计数责任在打包完成之后**（§2.2）——因为扩窗会往里加槽位（§10），而扩窗发生在 `rank/`。
