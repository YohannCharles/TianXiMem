# rank/ — 排序、扩窗、打包（§11 主线）

**PRD**：§10（Neighbor Expansion）、§11.2（Rerank）、§11.3（Context Packaging）、§6.4（token 预算）

## 要写什么

```text
reranker.py   自托管 cross-encoder
neighbor.py   §10 扩窗与回填（SQL 在 store/）
packaging.py  §11.3 渲染 + 打包 + 组内/组间顺序
```

**本目录是"排序 → 扩窗 → 打包"三连环的落地点，顺序不可换。**

**为什么是主线**：§4 的四条独立证据指向同一结论——**检索不是瓶颈，选择和排序才是**；外加一条规则理由（§11.1）：§2.3 把 embedding 与 LLM 都钉死了，**只有 Reranker 不作规定**——**这是唯一能自己投入算力的环节**。完整论证见 PRD §4 / §11.1。

## 1. Rerank（§11.2）

自托管开放权重的 cross-encoder。

> **reranker 只重排证据、不生成答案**，不触碰"`Search` 不得生成最终答案"的红线（§2.1 / §11.2）。

### 模型选型：Step 3 前定（§11.2）

**2026-09-23 决定：Step 3 前再选。** 选型受两条约束：

| 约束 | 说明 |
| --- | --- |
| **显存是硬约束** | 要与 qwen3.5-9b 和 BGE-M3 **共存于同一张卡**。**Step 0 就要把这条跑通**——否则 §1 的"显存预算"前提悬空、R1 的对冲方案要重写。预算表见 [`../../deploy/CLAUDE.md`](../../../deploy/CLAUDE.md) |
| 数据以英文为主 | **多语言能力非必需但便宜**（§12.2） |

> 顺带记住：reranker 是整份规则里**唯一不限模型**的组件，选型时**不必迁就 `text-embedding-v4`**。**显存不够时第一个该动的是它。**

### 顺序与预算的配合

**rerank 给出种子名次后，按名次依次扩窗，直到 Top-K 槽位用尽。**

这样预算不足时被牺牲的是**名次最低的种子**，而不是随机某一个。

## 2. Neighbor Expansion（§10）

**顺序：本步骤在 Rerank 之后执行**，理由见 §11.2。它是"**排序 → 扩窗 → 打包**"三连里的第二环，**不是"扩窗 → 排序"**。

```sql
SELECT * FROM qa_pairs
WHERE user_id = ? AND session_id = ? AND pair_idx BETWEEN ? - 1 AND ? + 1
ORDER BY pair_idx;
```

`UNIQUE(user_id, session_id, pair_idx)` 建出的索引**正好就是这个查询的键**。窗口从 ±1 改 ±2 **只需改 `BETWEEN` 的界**（§10）。

> SQL 本身在 [`../store/`](../store/)；本目录负责**调度与预算**。

**完整流程**：

```text
1. 融合后的候选 → Rerank
2. 取名次前 20 作为种子
3. 按名次依次扩窗（±1）
4. 去重
5. 回填，直到槽位用尽
```

### 三条预算约束

| # | 约束 |
| --- | --- |
| 1 | **注意粒度**：单位是 **QA 对**，所以 `±1` 拿回的是前后各**一整对（最多 4 条消息）**，不是前后各一条消息——**扩窗比 message 粒度时更贵** |
| 2 | **邻域槽位占 `top_k` 名额**。最坏：20 种子 × 每颗最多 3 槽 = **60 个槽位**，给回填留 40 个余量 |
| 3 | **真正先撞上的限制是 token 而不是槽位**（§6.4）：一对的文本量约为单条消息的两倍，117,760 token 的答案窗口可能**比 100 个槽位更早用尽** |

实际通常远小于 60——**种子密集时相邻窗口大量重叠，去重会折叠掉大部分**；种子分散时才逼近 60。

> **种子数、窗口大小、Top-K、token 预算，是同一道题，任何一项调整都要重算其余三项。**

**目的**：避免检索到正确的局部信息，却丢失事件背景、原因或状态变化。

### 重叠窗口的归属

重叠窗口在去重后**归属名次更靠前的那个种子**（§11.2）——这决定了组间顺序。所以 `neighbor.py` **不能只做"去重"**，还要把归属信息带出来给 `packaging.py`。

---

## 3. 顺序（§11.2 的两条规则）

### 组内顺序：按 `pair_idx` 时间序，**不把种子提到最前**

理由：窗口是一段连续对话，**按时间序读才成立**；把种子抽到最前会把一段话**拦腰截断**。而答案阶段按前缀截断——**窗口整体连续，意味着截断点落在窗口边界上**，不会切出半个窗口。

### 组间顺序 = 种子名次序

最终 `data` 数组是"**按种子名次依次排列的各窗口**"。答案阶段按这个顺序取前缀，所以**名次最高的种子及其邻域必须排在最前**——这正是"按名次依次扩窗"的用意。

> **组内与组间顺序都是可消融项**（§11.2）。若实验显示"种子提到最前"更好，**只改组内这一处**，不牵动其他环节——这是 §13"开关必须只影响它命名的那一件事"的一个具体例子。

## 4. Context Packaging（§11.3）

返回的 `content` 字符串会被**原样注入答案 prompt**（AML 侧仅按 `memory_text()` 做字符串拼接），因此**打包只能做在 content 里**，靠不上任何外部结构。

### 渲染是 `common/render` 的唯一实现

`content` = 该 QA 对的**渲染文本**，且**同一份渲染必须同时用作 embedding 的输入**（§7.2）——两处一旦不一致，"检索命中的是什么"与"模型读到的是什么"就会**漂移**，而**这种漂移不会报错**。

**本目录不自己拼字符串**，调 [`../common/`](../common/)。

### 渲染模板（v1 初值，Step 3 定稿）—— **本节是模板的唯一声明处**

```text
Q: {question}
A: {answer}
```

- `question` 为空的对（§6.2 的"批次以 assistant 开头"）**只输出 `A:` 那一行**
- `answer` 暂缺的 `pending` 对**只输出 `Q:` 那一行**
- **模板本身是"贵"消融项**：改模板就等于改变 embedding 输入，**整个向量索引要重建**。**所以要趁早定稿，别拖到 Step 5 之后**

**一个对里有多条非 user 消息时，每条带 role 标记**：

```text
Q: What time does the train leave?

A: [assistant] Let me check the schedule.
[system] {"tool": "schedule.lookup", "result": "09:42"}
[assistant] It leaves at 09:42.
```

- 不加标记的话，这几段在模型眼里**连成一片**，分不清哪句是助手说的、哪句是工具输出
- **标记会一并进 embedding 输入**（§7.2 要求同一份渲染），所以它**同时影响检索**——这是**有意的，不是副作用**
- **`role` 的取值域以 AML 实际传入为准，不要硬编码只认 `user` / `assistant`**

### content 必须自定界（§11.3）

AML 把多个返回项拼进答案 prompt 时只做 `"\n".join(...)`——**不插分隔符、不编号、不重复 `id`**。因此：

- 每项要能**独立读懂**，**不要把跨项才成立的结构（如"接上条"）放进 content**
- **首尾不要留空白**，否则拼接处会粘连
- **`Q:` / `A:` 这类行首标记是必要的**——没有它们，两个相邻项在模型眼里就是一段连续文本

### 打包策略

```text
1. 去重
2. 原文优先，不以任何摘要或合成文本替代
3. 同一 session 相邻信息尽量连续
4. 保留时间信息（原始表述）
```

> 第 2 条 v1 **自动满足**——**v1 不产生任何合成文本**（§11.3）。留待 v2。

## 5. 时间处理的**实现要点**

> **总规则（"不要在 content 里注入绝对时间戳前缀"及其两条裁判依据）在根 `CLAUDE.md`，已加载——本节只写本目录要落地的部分。**

| 要求 | 说明 |
| --- | --- |
| **筛选走 `event_time` 列** | 正文**只保留原始时间表述**，不做任何格式改写 |
| **`created_at` 必须始终带上** | CL-Bench 那条路径靠它渲染时间；不返回就等于放弃该数据集的时间信息 |
| **只给到日粒度**（如 `2026-07-26`） | **粒度会被模型看见**——给秒级时间戳，模型更容易按秒级回答，从而踩中"粒度变细"规则 |
| **不要用裸 Unix 毫秒** | 渲染出来是 `- [1753512557000] ...`，**对模型无意义** |
| `event_time` 为 NULL 时**发空串 `""`** | 渲染代码是 `str(item.get("created_at") or "")`，假值会退化成 `- {text}`，是一个**有定义的降级路径** |
| **不要拿 Add 的到达时间兜底** | 那是"何时写入"而不是"何时发生"，会给模型**错误信息** |

**粒度的收益属待验证**，与 §13 的 T1（时间戳前缀 带/不带）同批测。

### `score` 返回单调递减的占位值

**不要返回原始 RRF 分数**——融合分数**不是校准量**（§8），对我们没有意义；但**万一 AML 按 `score` 重排，省略 `score` 就有风险**。

取最安全的一侧：返回 `1/(rank+1)` 这类单调值——**无论 AML 是否重排，顺序都不变**。

## 6. Token 预算（§6.4）

| 要求 | 说明 |
| --- | --- |
| **双预算截断** | **同时按槽位数与 token 数**——否则排在后面的对会整段作废，白白占掉名额 |
| **tokenizer = `o200k_base`** | 用**答案模型自己的分词器**。**不要用字符数或空格切分近似**——单次近似偏差会在 100 个对上被放大到几千 token |
| 上限 **117,760** | 答案窗口 128k 扣掉输出与安全余量 |

> ### ⚠ 又一处 R1 类风险（§6.4）
>
> 本地 qwen3.5-9b 的分词器与 `gpt-4o-mini` **不同**，**本地量出的"能装多少对"不能直接搬到线上**。§12.1 的四条对冲里**没有这一条**，PRD §6.4 明确"应补上"：
> **Step 5 切换后必须重新量一次单请求实际返回的对数**，且 token 预算要做成配置项。见 [`../../../docs/open-questions.md`](../../../docs/open-questions.md) **E7**。

**token 计数实现在 [`../common/`](../common/)**——本目录只消费它，不自己数。
